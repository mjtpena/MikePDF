# ADR-0011: Printing
- Status: **Proposed.** Measured on one machine and one virtual printer (Microsoft Print to PDF). Physical PCL, PostScript, duplex and ARM64 printing, the XPS route and the PrintManager runtime path are unverified
- Date: 2026-11-02
- Deciders: Opus (approver), Sonnet (S12 evidence)

## Context
§8.10 asks for printing through "the WinUI print integration or the Windows print APIs (decide in an ADR)", rendering "at printer DPI through the engine, banded to cap memory", with page ranges, odd/even, scaling, auto-rotate, annotations and form-field options and a "print as image" fallback. Design decision Q1 recommends a **MikePDF print sheet** because the system dialog cannot show a preview of our engine's tiles or the annotation and form options together. [print](../features/print.md) 3.1 listed the criteria and left the choice open. The evidence is in [S12](../spikes/S12-print.md):

- **The engine can only produce bitmaps in the shipped sandbox.** Printing APIs do work inside a zero-capability AppContainer (`OpenPrinter`, `DocumentProperties`, `CreateDC`, a full job to a folder the container can write; a folder it cannot write was refused by the spooler). But with the engine's creation-time **prohibit-dynamic-code** policy (ADR-0004 decision 2) the printing path kills the process (`0xC000041D`) right after `OpenPrinter`. Every other `SandboxPolicy` mitigation, and the runtime Microsoft-signed-only policy with the inbox driver, were compatible. So `FPDF_RenderPage` into a printer DC is not possible from the engine as specified.
- **Raster printing from the broker works** (GDI `StretchDIBits` of engine bands) to Microsoft Print to PDF for ranges, odd/even, fit, shrink, actual and custom scaling, auto-rotate, paper size, collate and copies (a 3-page range with 2 collated copies produced 6 pages). The driver kept paper, copies and collate, and **cleared duplex** because the queue has none. The printed pages matched the engine's render at SSIM 0.993 to 0.999 (printer resolution, box-filtered). The queue stores the bands as JPEG.
- **Cost**: for 100 A4 pages at 600 dpi the broker spent about 20 s rendering and sending; the printer queue spent about 6 minutes converting. The broker's private bytes peaked at 152 MiB, flat from 1 to 100 pages, **but not reduced by banding**: whole-page bitmaps and 16 MiB bands peaked alike, and 4 MiB bands peaked higher. One device-resolution page is the cost, so the dpi caps it (300 dpi: 65 MiB). The spooler-side process grew from 108 to 410 MiB over 1 to 100 pages.
- **`PrintManager` / `PrintDocument`** is documented for Windows App SDK desktop apps and ships in 2.5.1's metadata; `PrintManager.IsSupported()` was true and `GetForWindow` worked in an unpackaged process. Its behaviour (flyout, preview, pagination) needs a visible window and was not run. An open WinUI issue says it works in full trust and not in partial trust, and was unreliable on older Windows 10 builds.
- A **handed-off PDF** has no print verb on this machine (the default handler is Edge with `open` only) and loses the preview, the settings and the privacy position.
- `IPrintDocumentPackageTarget` (XPS) can be created for the printer from an unpackaged process and offers two package target types; no page was authored or sent.

## Options considered
1. **(a) `PrintManager` / `PrintDocument`** with the system flyout. For: system preview and options, documented in Windows App SDK. Against: pages are XAML elements (an `Image` per band or page; memory unmeasured); needs a shown window; the options we need (annotations, forms, image mode, range grammar) live in a bounded custom area; not what Q1 chose; runtime unverified; open issues.
2. **(b) A MikePDF print sheet and GDI printing from the broker** (`EnumPrinters`, `DeviceCapabilities`, `DocumentProperties`, `CreateDC`, `StartDoc`, `StretchDIBits` of engine bands). **Chosen.** For: prototyped and measured; every §8.10 option is ours; works under Native AOT (a spike published and ran); no dependency on XAML; the engine stays bitmap-only. Against: raster output (large, slower), memory is one page at device dpi, no vector text, driver conversion time is outside our control, duplex and copies are `DEVMODE`-level (older) semantics.
3. **(b2) The same sheet, sent as XPS through `IPrintDocumentPackageTarget`** with a Print Ticket. For: the modern route, Print Ticket carries duplex, collate and resolution faithfully, the target accepts compressed images. Against: needs XPS object-model authoring; not prototyped; fidelity, memory and speed unmeasured. Kept as the fallback.
4. **(c) `FPDF_RenderPage` into the printer DC.** For: vector output (12 times smaller than raster here, 4 times less own memory, SSIM 0.998). Against: impossible in the engine process while prohibit-dynamic-code is on; a separate print host needs a new sandbox profile and a negative-test suite; vendor drivers load into that process. A v1.x option.
5. **(d) Generate a print-ready PDF and hand it to the system.** Against: no `print` verb here; another application renders it, so no honest preview; settings do not reach it; the document leaves our control.

## Decision
1. **Printing is done by the broker with GDI, behind a MikePDF print sheet** (`ContentDialog`, design 11-print). The system's `PrintDlgEx` and `PrintManager` flyout are not used. "Printer preferences..." opens the driver's own dialog with `DocumentProperties(DM_PROMPT)`.
2. **Capabilities come from the spooler.** The options shown (duplex, collate, copies, colour, paper sizes, resolution) follow `DeviceCapabilities` and the printer's Print Schema capabilities (`prntvpt`). The driver's merged `DEVMODE` (`DM_IN_BUFFER | DM_OUT_BUFFER`) is the truth: what it clears is shown as not applied. The document's `/NumCopies` and `/Duplex` remain defaults only.
3. **Pipeline.** `PrintLayout` (pure, in `MikePDF.Core.Printing`) places each page; the broker asks the engine for bands (`RenderBand`, flags annotations / form fields / printing) and sends them with `StretchDIBits` in a worker thread, rendering band *k+1* while sending band *k*. One printer DC and one `StartDoc` per job. Cancel calls `AbortDoc` (7.5 ms measured) and deletes any 0-byte output the spooler left.
4. **Memory is capped by pixels per page, not by band size** (this supersedes print.md 3.5's reading of "bands cap memory"). The device dpi is `min(printer dpi, 600)`, lowered for large pages so a page is at most about 40 Mpixels (A4 at 600 dpi is 35 Mpixels and cost about 140 MiB); "print as image" is at most 300 dpi; documents that allow only low-quality printing are capped at 150 dpi. Band size stays a pipelining detail (default 16 MiB, 8 to 9 bands per A4 page at 600 dpi). The page-count independence of PRINT-10 stands for MikePDF's own processes; it is not asserted for the spooler.
5. **Fidelity test (PRINT-13) is redefined**: compare at the printer's resolution with a 4x box filter on both sides, threshold **SSIM >= 0.99** for the Print To PDF cell (measured 0.993 to 0.999 on the fixtures; the 150 dpi comparison scores 0.93 to 0.98 even with no printing, so it is kept only as a control). Print To PDF writes JPEG, so byte-exact comparison is not possible there.
6. **Threads.** `StartDoc`, `StretchDIBits`, `EndPage` and `EndDoc` run off the UI thread; `EndDoc` blocks for seconds on the PDF queue.
7. **The sandbox is not weakened.** The engine keeps prohibit-dynamic-code and never receives a printer DC. Vector printing (candidate c) is deferred to a possible v1.x print host with its own profile, ADR and negative tests.
8. **Fallback**: if a driver mishandles GDI bands, "print as image" (one bitmap per page, at most 300 dpi) is the first fallback; the XPS route (b2) is the second and needs its own spike before use.

## Consequences
- The engine and protocol need `RenderBand` (print.md 11) and the print flags; no engine change for printer access.
- The print sheet, preview, capability reading, `DEVMODE` handling and a worker for job execution are MikePDF-owned code. P/Invokes (winspool, gdi32, prntvpt) go through CsWin32 `NativeMethods.txt` in the broker.
- Raster output is large (about 3 MB per A4 page at 600 dpi to the PDF queue) and slow on virtual queues (3.8 s per page at 100 pages); a physical printer may be better or worse. Users see this as "Printing page n of N" with Cancel.
- The test matrix: the Print To PDF cells can be automated; **no XPS Document Writer queue exists on this machine** (OQ-PRINT-7: use Print To PDF as the "A" cell and add an XPS cell only where the queue exists); the 1,000-page 600 dpi cell is impractical as a routine test (about an hour, 3 GB) and should be a manual or reduced-dpi run.
- print.md edits: 3.5 (bands do not cap memory, 8 to 9 bands per page, dpi cap), 3.1 and OQ-PRINT-2 (decided), 14 (XPS cell), PRINT-10 and PRINT-13 (above), plus a note that `AbortDoc` can leave an empty output file.
- Follow-ups: S12b on a duplex printer, a PCL and a PostScript class driver to FILE (needs the user, OQ-PRINT-8, -9); an XPS spike if drivers misbehave; the Narrator pass on the print sheet; an ARM64 class-driver run (R2).

## Verification
- The §8.10 matrix cells marked A pass on Microsoft Print to PDF: page counts and sizes, range, odd/even, scaling, auto-rotate, annotation and form flags, print as image, the SSIM test above, cancel (queue empty, engine idle in under 1 s).
- Own-process peak private bytes for a 100-page A4 600 dpi job stay within 5% of a 10-page job and below about 200 MiB (measured 148 and 152 MiB); a 1,000-page run is **not measured** and the spooler's growth (108, 134, 410 MiB at 1, 10, 100 pages) is checked there.
- Duplex and collate reach a real duplex printer's driver (manual; not measured).
- If the engine or broker cannot render and send a page faster than the printer converts it, or a driver rejects banded blits, revisit with the XPS spike (decision 8).
- Revisit this ADR if a v1.x print host is proposed, if Windows App SDK documents printing limitations for 2.x, or if a physical-printer run contradicts the memory behaviour (decision 4).
