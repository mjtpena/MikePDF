### 2.2 Fixtures

All generated by `spikes/S4/gen/Fixtures.cs`, classic xref, no object streams, so object numbers are known:

- `base.pdf`: one page, real Helvetica text on five lines plus an empty lower area for shapes. Markup quads come from `FPDFText_FindStart`/`FPDFText_CountRects`/`FPDFText_GetRect` over the real phrases, and the check re-reads the text under each annotation with `FPDFText_GetBoundedText`.
- `forms.pdf`: AcroForm with nine fields: text single, multiline, comb (MaxLen 8), checkbox, radio group of two, combo (not editable), combo (editable), list (multi-select), push button. Every widget starts with a valid empty `/AP`, as Acrobat-made forms do.
- `signed-base.pdf` and `signed-forms.pdf`: the two above plus an empty signature field, then signed with a throw-away self-signed RSA-2048 / SHA-256 certificate (`adbe.pkcs7.detached`, 16 KB placeholder, `/ByteRange` patched in place). Both verify (`SignedCms.CheckSignature`, signature-only) before any edit. This is a minimal stand-in for S8's fixtures, built here so the signature column is not empty.
- PDFium test corpus (`spikes/_shared/corpus/pdfium-resources/`): `multiple_form_types.pdf` (a form with **no** `/AP` anywhere, cases B10 to B12) and 20 foreign files for the incremental-save probe (3.5), 9 of which use xref streams. The corpus signatures (`two_signatures.pdf`, `signature_reason.pdf`) have placeholder `/Contents`, so they are used only for "does the signature dictionary survive", not for cryptography.

### 2.3 Operations and saves

- **39 cases** produce **100 output PDFs**: 17 annotation cases through the PDFium API (A01 to A14, with variants), 6 annotations written by Quire (Q01 to Q06), 12 form cases (B01 to B12), 4 signature cases (G01 to G04).
- Every PDFium case is applied to a fresh document opened with `FPDF_LoadCustomDocument` (callback reads from an in-memory buffer, like the broker handle model), with a form-fill environment (`FPDFDOC_InitFormFillEnvironment`, version 1, all callbacks null). Saving uses `FPDF_SaveAsCopy` through an `FPDF_FILEWRITE` callback into a byte buffer.
- Each case is saved as `FPDF_INCREMENTAL` (**inc**) and `FPDF_NO_INCREMENTAL` (**full**). Annotation cases get two more saves, **incR** and **fullR**, where the page is rendered with `FPDF_RenderPageBitmap(..., FPDF_ANNOT)` **before** the save. I added them after the first run showed that PDFium builds appearances in memory when the annotation list is built (at render time) and writes them if present. "Cold" in the tables means no render before the save, "rendered" means incR/fullR.
- Form values are set only through form-fill events: `FORM_SetFocusedAnnot`, `FORM_SelectAllText`, `FORM_ReplaceSelection`, `FORM_SetIndexSelected`, `FORM_OnLButtonDown/Up`, `FORM_ForceToKillFocus`. No `FPDFAnnot_SetFormFieldValue`-style setter exists in the headers.
- **Quire-authored cases (Q01 to Q06)** exist because PDFium cannot do some operations. `RawAnnots.cs` appends objects as an incremental update (new objects, new page `/Annots`, new xref section, `/Prev`) and writes the appearance streams by hand. They stand in for `Quire.PdfWriter`. Their "full" output is PDFium loading the Quire-authored file and saving it with `FPDF_NO_INCREMENTAL`.

### 2.4 Checks per output

1. `qpdf --check`: exit code and warnings. `pass` is exit 0, `warn` is exit 3, `FAIL` is exit 2. For the corpus probe, warnings that the **original** file already produces are subtracted.
2. `qpdf --json=2` object inspection: annotation dictionaries, whether the page `/Annots` element is direct or indirect, `/AP /N` kind, `/BBox`, `/Resources`, key types, `/NeedAppearances`, field `/V` and `/AS`, decoded AP stream text.
3. Fresh-session PDFium reopen (the check is a separate process): subtype, `/Rect`, `/Contents`, colour (`/C`, read from the file because `FPDFAnnot_GetColor` fails once an AP exists), `QuadPoints` count, `InkList` count, `/Line`/vertex readability, `/Popup` and `/IRT` resolution through `FPDFAnnot_GetLinkedAnnot`, `/Name` value type, text under the annotation, field value, checked state, selected options.
4. PDFium render at scale 1.5 with `FPDF_ANNOT`, no appearance regeneration by us. Form and signature pages also call `FPDF_FFLDraw` with the form handle (the form layer draws widgets and may itself regenerate an invalid AP); annotation pages do not. pdf.js render at the same scale. **"visible" means at least 40 pixels changed (20 for form widgets) against a render of the unmodified input by the same engine** (within the annotation rect plus 6 pt for annotations). It says "drawn", not "drawn correctly". I judged correctness by eye on contact sheets (`out/sheets/`): annots-1 to 4, annotsR-1 and 2, forms-1 and 2, sig-1. Every cell listed as visible looked right, with the exceptions called out in section 4. annotsR-3 (A13b, A14) was not opened; those two rely on the pixel diff.
5. Incremental saves: the original bytes must be an exact prefix of the output. Signature cases: signature count, `/ByteRange` and `/Contents` before and after through `FPDF_GetSignatureObject`, and `SignedCms.CheckSignature` with the **original** ByteRange applied to the **new** file bytes.
6. Objects written by each incremental save (scan of the appended region).

### 2.5 What was not done, and why

- **Acrobat Reader and Edge**: not run. Acrobat is not automated (R-15); Edge has no headless capture that draws a PDF. `spikes/S4/out/manual-acrobat-checklist.md` lists every output file with what to look for and blank result cells. 72 matrix cells are "not measured" for this reason.
- **Chrome**: uses PDFium, so it duplicates the PDFium column. I also tried headless capture of Chrome 156 and Edge 156 (`--headless=new --screenshot` on `A01.incR.pdf`): both returned a 900x1200 frame with **one** colour (checked pixel by pixel), because the headless browser does not render the PDF viewer. Evidence in `out/headless-attempt/`. Not measured.
- **Firefox**: not installed. pdf.js is the stand-in.
- **Colour fidelity, opacity (`/CA`) and blend behaviour in Acrobat**: not measured. Only the PDFium-generated Highlight AP was inspected (`/BM /Multiply`).
- **DocMDP and certification permissions**: not measured (S8).
- **Rotated pages, CropBox offsets, encrypted files, files with object streams as the *source* of an annotation edit beyond the probe**: not measured.

### 3.7 Failing cells, explained at object level

Clause numbers are ISO 32000-2:2020 where I am confident they match ISO 32000-1:2008 numbering (the annotation and form clauses are unchanged between the two). Where I am not sure of a number or table, the text says "clause to confirm".

**F1. No `/AP` in a cold save (A01, A02, A03, A04, A05, A06a, A07a, A08, A09, A13a: 10 cells; A13a also after render).**
Saved object, A01 cold (page object 3, annotation embedded in `/Annots`):
`/Annots[<</C[1 .92156863 0]/CA 1/Contents(...)/F 4/M(...)/NM(...)/QuadPoints[137.124 698.736 219.984 698.736 137.124 687.624 219.984 687.624]/Rect[...]/Subtype/Highlight/T(Quire Tester)/Type/Annot>>]`.
There is no `/AP`. The `/AP` entry is optional in the annotation dictionary (12.5.2) and a conforming reader is free to synthesise or to draw nothing (12.5.5, clause to confirm for the exact wording). The measured fallbacks differ: pdf.js synthesises Highlight, Underline, StrikeOut, Squiggly, Square, Circle and Ink (1,962 changed pixels for A01 with no `/AP` in the file), but draws **nothing** for Text (A05), FreeText (A06a) and Stamp (A13a): "INVISIBLE" in the pdf.js cold cells. PDFium's own render draws all but the name-only stamp because it builds the AP in memory at render time. For A13a nothing draws anywhere, because PDFium has no default appearance for a Stamp and there are no objects to build one from.
After a render, the same annotation carries `/AP << /N 9 0 R >>` with `/PDFIUM_HasGeneratedAP true`; the stream is `/Subtype /Form /BBox [137.124 687.624 219.984 698.736] /Matrix [1 0 0 1 0 0] /Resources << /ExtGState << /GS << /BM /Multiply /CA 1 /ca 1 >> >> >>` with content `/GS gs 1 .92156863 0 rg ... f`. That is a correct appearance on paper (11.6.3 blend modes). Rendering in Acrobat: **not measured**.

**F2. Popup and reply links lost (A05).**
Saved cold: parent Text has no `/Popup`; the Popup annotation has no `/Parent`; the reply is a second Text annotation whose `/IRT` is the **string** `(s4-text-0001)` and which has no `/RT`. `FPDFAnnot_SetStringValue` is the only writer and it always writes a string ("The value type would be FPDF_OBJECT_STRING after this function call succeeds", `fpdf_annot.h`). 12.5.6.2 (markup annotations, `/IRT` and `/RT`) and 12.5.6.14 (Popup: `/Parent`, `/Open`) require indirect references. After reopen in a fresh session `FPDFAnnot_GetLinkedAnnot` returns NULL for both. Even if a setter existed, the annotation is a **direct** dictionary inside `/Annots`, and a reference can only point to an indirect object (7.3.10). The Quire-authored Q04 (indirect objects, `/Popup`, `/Parent`, `/IRT`, `/RT /R`, `/StateModel /Review`, `/State /Accepted`) round-trips: reopen resolves all links, and PDFium's own full re-save keeps them.

**F3. Stamp `/Name` is a string, not a name object (A13a, A13b).**
Saved: `/Name(Approved)`. Expected `/Name /Approved` (12.5.6.12, rubber stamp entries, Table 184 in the 2008 numbering: clause to confirm). `FPDFAnnot_GetValueType` returns 3 (string) instead of 4 (name). A viewer that maps standard stamp names to built-in artwork will not match a string. Q05 writes the name object correctly.

**F4. A06b FreeText AP has no `/Resources` and no `/Matrix`.**
`FPDFAnnot_SetAP` takes only the content stream text. The resulting stream dictionary has `/BBox [300 300 520 350]` and nothing else, yet the text drew in PDFium and pdf.js. It resolved `/Helv` from the **page's** resources, which this fixture happens to define. On a page without `/Helv` the text would drop. Inheriting resources from the page for a form XObject is a PDF 1.1 compatibility behaviour that ISO 32000 marks as deprecated (clause to confirm), so this is a latent fidelity risk, not a measured failure. Acrobat: **not measured**.

**F5. Line, Polygon, PolyLine (A10, A11, A12).**
`FPDFAnnot_IsSupportedSubtype(Line|Polygon|PolyLine)` returns 0 and `FPDFPage_CreateAnnot` returns NULL, as the header's list of creatable subtypes says (circle, fileattachment, freetext, highlight, ink, link, popup, square, squiggly, stamp, strikeout, text, underline). No setter exists for `/L`, `/LE`, `/Vertices`, or an array at all. Q01, Q02 and Q03 (dictionary plus hand-written AP with arrowheads, 12.5.6.7 and 12.5.6.9) pass every check and render the same in PDFium and pdf.js.

**F6. Ink `/Rect` rewritten.**
Requested `[90 230 330 290]`, saved `[88.5 228.5 331.5 291.5]`: `FPDFAnnot_AddInkStroke` grows the rectangle by the border width. Counted as ok in the matrix (the saved rect contains the requested one), recorded here because Quire's selection geometry must read it back.

**F7. Signature full copies (G01 to G04 full: 8 cells).**
`FPDF_NO_INCREMENTAL` rewrites every object, so the original bytes are not a prefix (4 cells) and the CMS digest over the original ByteRange no longer matches (4 cells). The signature dictionary itself survives verbatim (`/ByteRange` and `/Contents` unchanged, count 1 to 1), so the file looks signed but the signature is broken (12.8.1, ByteRange covers absolute byte offsets). Expected behaviour; it is the reason §7.5 step 5 defaults to incremental and warns before anything that forces a full copy.

**F8. Invisible cells (5).**
A05 and A06a in pdf.js cold (no `/AP`, and pdf.js does not synthesise Text or FreeText appearances on the canvas); A13a in PDFium, in pdf.js cold and in pdf.js rendered (no `/AP` and no page objects for PDFium to build one from). Same cause as F1.

**F9. xref streams (corpus probe, not in the tally).**
Appended tail for `bug_1029.pdf`: `49 0 obj <</Info 4 0 R /Root 1 0 R /Size 50/Prev 54297/ID[...]/W[0 4 1]/Index[1 1 2 1 ...]/Length 90>>stream ... endstream` followed directly by `startxref`. Three defects against 7.5.8 (cross-reference streams: 7.5.8.2 requires `/Type /XRef`; 7.3.10 requires `endobj`; the stream's own object must have an entry, clause to confirm). qpdf: `(xref stream: object 49 0, offset N): expected endobj`, `file is damaged`, `xref not found`, then reconstructs.

## 4. Surprises

1. **Output depends on whether the page was rendered before the save.** Same operations, same API calls: cold save has no `/AP`, post-render save has `/AP`. In the app the user's annotation is rendered long before Save, so the app would see the "rendered" behaviour, but a batch or headless path would not. Neither is under Quire's control unless Quire writes the AP itself.
2. **A private key leaks into the file.** `/PDFIUM_HasGeneratedAP true` is written into every annotation whose AP PDFium generated. Harmless to viewers, noise in the file, and it marks "PDFium regenerates this on load" (we saw PDFium persist generated APs for the reply and state annotations in Q04 full: the Quire-authored file gained two PDFium APs and the key).
3. **Annotations created through the API are direct dictionaries** in the page's `/Annots` array. This is why no linking is possible and why any later incremental edit of one annotation rewrites the whole page object.
4. **An incremental save is never "just the new annotation".** Page 1's catalog, page tree, page, content stream (re-compressed with Flate; `base.pdf`'s was uncompressed) and font objects are re-emitted, plus a new second half of the trailer `/ID`. A one-field edit on the forms fixture (B01) wrote 25 objects: those same six plus every widget and field object and every AP stream PDFium had loaded. A no-op open-and-save of the signed fixture appended 1,381 bytes and 7 objects (catalog, pages, page, content, two fonts, signature widget) and the signature still verified. Growth across the 20-file corpus on a no-op save: +24% to +270%; `bug_717.pdf` went from 79,942 to 158,579 bytes for 8 objects. This confirms S1's observation that incremental save of an unmodified document is not a no-op (ADR-0002).
5. **xref-stream originals get an invalid appended xref** in 7 of 9 cases; the other 2 got classic xref sections. Full copies are classic xref sections and introduced no structural damage in 20 of 20 files (one extra qpdf warning in `bug_707673.pdf`: a widget not reachable from `/AcroForm`), and are sometimes much smaller (`bug_1029.pdf` 54,666 to 28,395 bytes).
6. **PDFium regenerates appearances for every AP-less widget it loads, not only the edited field.** Filling one text box in `multiple_form_types.pdf` (B10) left 5 of 6 widgets with new `/AP` streams. For forms that already have APs (B01 to B09) PDFium rewrote the **checkbox and radio state streams** with its own artwork (compare the original ZapfDingbats tick with the saved one on `sheets/forms-1.png`), replacing the author's design while keeping `/AS` and `/V` correct.
7. **pdf.js cannot serve as an "AP-reliant viewer" probe.** It synthesises appearances for 7 annotation types when `/AP` is missing, so "visible in pdf.js" does not prove the file has an AP. The `/AP`-in-file column from qpdf is the authoritative signal, and the Acrobat and Edge passes remain the real test.
8. **PDFium wrote nothing by default** (3.6): no flags, author, dates, id, colour. Everything §8.2 lists must be set by Quire.
9. **FreeText via `SetAP` works only through page-resource fallback** (F4).
10. **Headless Chrome and Edge do not draw PDFs** (2.5).
11. **`FPDFAnnot_SetColor` alpha does not appear as `/CA`** in the one case checked: A=255 gave `/CA 1`. Behaviour for A below 255 is **not measured**.

## 5. Recommendation

### 5.1 Direction for ADR-0008 (proposal, Opus decides)

1. **Quire owns annotation dictionaries and appearance streams.** Do not rely on PDFium's in-memory generation or `FPDFAnnot_SetAP`. Evidence: F1, F2, F3, F4, F5, surprise 1. The Quire-authored Q01 to Q06 prove the approach: every one passes `qpdf --check`, reopens with all properties in a fresh PDFium session, and draws in PDFium and pdf.js.
2. **PDFium remains the engine for reading, rendering, text, form filling and page operations.** For forms it works (12 of 12 value cases, appearances regenerated, no `/NeedAppearances` needed).
3. **Save as two stages**: PDFium writes its incremental update for form and page changes, then `Quire.PdfWriter` appends its own incremental update for annotation objects (new objects, replaced page `/Annots`, xref, `/Prev`), as `RawAnnots`/`Fixtures.Append` do. Appending preserves the earlier bytes by construction (checked on every Q case). Reload in PDFium before further editing, which §7.5 step 2 already requires for validation. If Opus prefers a single stage, the alternative is for Quire to write the whole update itself and use PDFium only to read.
4. **Never call incremental save when nothing changed** (surprise 4, ADR-0002 already says this).
5. **Validate and repair the output tail** before the atomic replace: parse the xref chain; for an appended xref **stream**, rebuild it (type, own entry, `endobj`) or convert to a classic section if the spec permits (clause to confirm for appending a classic table after a stream `/Prev`). A two-patch repair is not enough (3.5). Fall back to `FPDF_NO_INCREMENTAL` (no structural damage in 20 of 20 probe files) only when the document is unsigned.
6. **Strip `/PDFIUM_HasGeneratedAP`** from anything Quire saves.
7. **Policy for existing author appearances**: PDFium replaces checkbox and radio state streams on any form edit. Decide whether to keep the original stream when only a different state is selected (surprise 6).
8. **Seed the §12.4 harness from this spike**: `spikes/S4/check` already does the qpdf, reopen, render and signature steps. It needs Acrobat and Edge screenshots on VM-V added.

## 6. Go / No-go

**GO, provisional on the Acrobat and Edge manual pass.**

The plan's rule: go if every gap can be closed by Quire writing its own appearance streams and dictionaries through the PDFium edit APIs or `Quire.PdfWriter`; no-go if PDFium's incremental save corrupts existing signatures or produces structurally invalid output that cannot be post-processed.

- Signatures: **not corrupted.** 4 of 4 incremental saves on signed fixtures keep the original as an exact byte prefix, keep the signature count, `/ByteRange` and `/Contents`, and the CMS still verifies over the original range. The 2 corpus files with placeholder signatures also kept their signature objects through an incremental save. Full copies invalidate signatures, as expected.
- Structural validity: PDFium's incremental output is **invalid for xref-stream sources (7 of 9)** and valid for classic ones. It **can be post-processed** because the defect is confined to the appended tail, which the existing signature does not cover, but it needs a real xref rewrite, not two patches (3.5).
- Gaps: all 12 in 5.2 are closed by Quire-written objects. Q01 to Q06 demonstrate the five hardest (Line, Polygon, PolyLine, Popup/IRT/state, named stamp) plus a FreeText with a proper AP.

Why provisional: no result here shows that **Acrobat** or **Edge** draws the PDFium-written or Quire-written appearances, or opens PDFium's xref-stream output without a repair prompt. If Acrobat refuses or repairs the xref-stream output, step 5 of 5.1 becomes mandatory rather than hygiene. If Acrobat draws nothing for cold-saved markup, gap 1 is mandatory rather than defensive.

## 7. Open questions for Opus

1. **Single or two-stage save** (5.1 item 3)? A single `Quire.PdfWriter` update would remove the double write and the xref-stream problem but costs the whole object-graph update for forms and page operations.
2. **Who runs the Acrobat/Edge pass** and when? `spikes/S4/out/manual-acrobat-checklist.md` is ready (priority 1 files first, about 60). Needs Acrobat's signature-panel wording for G01 to G04 verbatim, which also feeds S8 and ADR-0012.
3. **Is pdf.js enough for the "Firefox" column** in §12.4, or do we install Firefox on VM-V? pdf.js is Firefox's engine but differs from the shipped build.
4. **Experimental API exposure (R-12).** The P/Invoke layer declares 51 Experimental functions (`fpdf_annot.h`, `fpdf_formfill.h`, `fpdf_signature.h`, `fpdfview.h`). If the recommendation is adopted, the annotation-creating ones (`CreateAnnot`, `SetAP`, `AppendObject`, `AddInkStroke`, `SetColor`, `SetBorder`) drop out of production use. Worth recording in ADR-0008 as a risk reduction.
5. **Standard stamp set**: which names and artwork does Quire ship (product decision), and do stamps follow Acrobat's names?
6. **Policy for author checkbox/radio appearances** (5.1 item 7) and for fields PDFium regenerates but the user did not touch (surprise 6).
7. **DocMDP**: PDFium rewrites the catalog, page tree, content stream and fonts on every incremental save, even in a signed document. Does Acrobat accept that for a certified (DocMDP) document? Not measured, belongs to S8 but this spike produced the files (`G01` to `G04`, `probe/two_signatures.*`).
8. **Corpus**: should the 20-file foreign-file probe become a permanent fixture set in the §12.2 corpus, and are any of those files problematic for redistribution (they are PDFium test resources, BSD-3-Clause)?
