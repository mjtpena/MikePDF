# S3: Process isolation and IPC

- Status: Complete, **provisional** (DEV-class machine). Sections up to the Appendix use a .NET engine stub; **S3b (end of file) adds the C++20 engine and supersedes the .NET-only caveats**
- Date: 2026-10-28
- Author: Sonnet (implementation). Reviewer: Opus
- Target ADRs: ADR-0004 (process model and sandbox), ADR-0005 (IPC transport and serialisation)
- Code: `spikes/S3/` (frozen for evidence). Raw outputs: `spikes/S3/out/results/` (gitignored, regenerate with `publish.ps1` + `run.ps1`)

## Questions

From the S3 plan section:

1. Can a full-trust process create an AppContainer profile and launch the engine in it with zero capabilities?
2. Can the engine connect to a named pipe whose DACL grants only the current user and the AppContainer SID, and map a section handle passed through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`?
3. Does PDFium's default Windows font path (GDI) render non-embedded fonts inside the AppContainer? If not, what is a broker-provided `FPDF_SYSFONTINFO` worth?
4. Which mitigation policies can the engine run under without breaking PDFium?
5. Does a Job Object memory limit stop a runaway engine cleanly, and can the broker detect it?
6. How does the low-integrity restricted-token fallback compare?
7. Timing: Ping RTT, RenderTile transport overhead, spawn to Hello, crash to restored tile, and the cost of the largest control message.

## Method

### Honest scope statement (read first)

- **The engine stub in S3 proper is a .NET 10 console exe that P/Invokes `pdfium.dll`, not the C++20 engine.** (A C++ toolchain became available later; see S3b at the end, which re-tests the points below.) What this changes:
  - *Conclusions that carry over to a C++ engine:* AppContainer profile and ACL mechanics, `HANDLE_LIST` inheritance, pipe DACL behaviour, `DuplicateHandle` into the container, Job Object behaviour, all negative-access results, Low-IL behaviour, PDFium inside an AppContainer (GDI font path, rendering into a shared section), pipe I/O flags, and which Win32 mitigation flags are accepted by the OS.
  - *Conclusions that do not carry over:* spawn time (about 36 ms of the 55 ms is .NET runtime start), engine memory footprint, anything about dynamic-code prohibition and Win32k lockdown (both broke the .NET runtime, a C++ engine needs its own test), JIT-related behaviour, and the managed-OOM behaviour in the memory-limit test.
- **Not packaged.** The launcher is a plain unpackaged exe. Whether a packaged full-trust MSIX process behaves identically (profile creation, `ALL APPLICATION PACKAGES` ACLs for the package directory) is **not measured**. S6.3 should repeat the launcher inside the MSIX.
- **DEV class only.** Intel Core Ultra 9 275HX (24 logical cores), 64 GB RAM, Windows 11 Home build 26300, active power plan **Balanced** (not "Best performance"; I did not change system settings), plugged in. R1 and R2 not available. Other agents were building on the same machine, so every timing run records system CPU (25 to 30 percent during the benchmark runs; it was **100 percent** during an early dry run, which gave 13 ms Ping medians and was discarded).
- **No true cold runs.** "Cold" needs a reboot or `RAMMap -Et` (needs admin). All timings are warm file cache. The first spawn of each configuration is reported separately as "first", but it is not a cold-cache number.

## Results

### R1. AppContainer launch (Q1, Q2): works

- Zero-capability AppContainer (`capabilityCount = 0`, token integrity `0x1000`, 2 privileges: change-notify and increase-working-set) runs the engine, PDFium initialises, a document opens from an inherited handle, tiles render into the shared section, the pipe works.
- **ACL requirements found** (the "real finding" the task asked for):
  - Framework-dependent .NET: **only the engine directory (inside the repo) needed an ACE**: inheritable `(OI)(CI)(RX)` for the AppContainer SID. `C:\Program Files\dotnet` is readable already through `ALL APPLICATION PACKAGES` (RX) and `ALL RESTRICTED APPLICATION PACKAGES` (RX) ACEs, and nothing in Program Files was touched. No ACE was needed on the parents of the engine directory (the AppContainer token holds `SeChangeNotifyPrivilege`, so traverse checking is bypassed).
  - Because `ALL RESTRICTED APPLICATION PACKAGES` is also on the runtime dir, `PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY` opt-out did **not** stop the .NET engine from running (it survived in the mitigation matrix). The opt-out is therefore not a usable hardening test for this layout. Not investigated further.
  - A self-contained publish (70 MB, in the repo) also works and removes the dependency on the machine-wide runtime ACLs. Startup is identical (see R6).
- Env: the system rewrote `TEMP` for the container to `%LOCALAPPDATA%\Packages\<name>\AC\Temp`; `USERPROFILE` stayed the real one (still denied).
- Pipe: DACL `D:(A;;FRFW;;;<user sid>)(A;;FRFW;;;<AppContainer sid>)`, random 128-bit name, created natively with `FILE_FLAG_FIRST_PIPE_INSTANCE` and `PIPE_REJECT_REMOTE_CLIENTS`. Verified with `pipeacl`:

  | Case | Result |
  |---|---|
  | DACL = user + engine's own container SID | connected; `GetNamedPipeClientProcessId` equals the spawned pid |
  | DACL = user only | engine fails with `UnauthorizedAccessException` |
  | child in a different AppContainer than the DACL names | engine fails with `UnauthorizedAccessException` |

  A **same-user, medium-IL process is allowed by the DACL** (the user ACE). The random name and the first-connect-wins single instance are the only defence against a same-user squatter, so the broker checks the connected client's pid (done, `ClientPidVerified`) and should do so in production.
- Handles: file handle (read-only, `FILE_SHARE_READ`) and section handle are passed through `HANDLE_LIST` (handles must be inheritable and `bInheritHandles = TRUE`; confirmed against the UpdateProcThreadAttribute docs). A second document is delivered later with `DuplicateHandle` into the container process. Both work, so "broker owns file I/O, engine never sees a path" is demonstrated.
- `FPDF_FILEACCESS.m_FileLen` is `unsigned long`, which is **32 bits on Windows**: this API cannot open files of 4 GiB or more. The stub rejects them. ADR-0002/0005 should plan for `FPDF_LoadMemDocument64` with a mapped section, or a PDFium patch, for huge files.

Reading the table:

- **ac-plain is not enough on its own.** Two rows are gaps with the AppContainer alone: **`CreateProcess(cmd.exe)` succeeds** (the container can launch a child inside itself; the child-process policy closes it) and **an unsigned DLL in a readable directory loads** (needs the signature policy). Both are closed in ac-hardened. The "load a DLL from a temp copy" row from the spec passes in ac-plain, but only because the file system denies the read, so it does not exercise the signature policy; the extra "unsigned DLL in engine dir" row does.
- **ac-hardened denies every negative test.** Nothing was found to be allowed that the spec says must be denied.
- **Low-IL is much weaker**: it still reads the user's documents, connects to the network, opens (VM_READ|DUP_HANDLE) all 49 same-user processes it can see, and reads the clipboard. Writes are blocked (mandatory integrity) and the registry is blocked. The CHILD_PROCESS_POLICY docs warn that the child restriction is only effective if the process cannot open privileged handles to other processes; Low-IL fails that precondition. So the Low-IL "child-process denied" cell is bypassable in principle (not exercised).
- The baseline column shows each test is capable of succeeding, including the UNC test (this user can open `\\localhost\c$`).
- `ui.clipboard.read` was never given content: only `OpenClipboard` and format availability were checked. Content was not read.
- The negative suite is one process lifetime per profile; it asserts denial of the attempted operations, not that the sandbox is escape-proof.

| DEP | survives | |
| ASLR bottom-up + high-entropy + force-relocate | survives | |
| Strict handle checks | survives | AppContainer tokens already report `StrictHandleCheck=0x3` by default |
| Extension-point disable | survives | |
| CFG always on | survives | |
| CET user shadow stacks `ALWAYS_ON` (compat mode) | survives | `POLICY2` second DWORD64; default `UserShadowStack` flags of any process here are `0x105`. Strict mode and whether PDFium/.NET modules are all `CETCOMPAT`: **not measured** |
| Font disable (non-system fonts) | survives | irrelevant for PDFium/FreeType; only affects GDI |
| Image load: no remote, no low label, prefer System32 | survives | |
| Child-process policy `PROCESS_CREATION_CHILD_PROCESS_RESTRICTED` | **survives, with a launch condition** | `cmd.exe` then fails with 367. **Must start the engine with `DETACHED_PROCESS`**: a console-subsystem exe started with `CREATE_NO_WINDOW` gets a `conhost.exe` child and dies with `0xC0000142` under this policy. A GUI-subsystem or detached engine is fine |
| All-application-packages opt-out | survives | see R1: `ALL RESTRICTED APPLICATION PACKAGES` keeps the runtime readable |
| **Win32k system call disable** | **fails (.NET)**: `0xC0000142` | Loaded-module list of the stub at Hello shows `shell32, user32, win32u, gdi32, gdi32full, imm32` loaded **by the .NET apphost itself**; their DllMain cannot init without Win32k. **Control:** native `cmd.exe` and `hostname.exe` started under the same AppContainer + Win32k lockdown ran normally, so the policy itself works on this OS. | **Prohibit dynamic code** | **fails (.NET)** | creation: `Failed to create CoreCLR, HRESULT 0x80070677` (`ERROR_DYNAMIC_CODE_BLOCKED`); runtime after JIT warm-up: the engine corrupts and then runs out of memory. ### R4. Job Object memory limit (Q5) (`out/results/memlimit.md`)

| Case | Result |
|---|---|
| native commit, per-process limit 512 MB (n=2) | `VirtualAlloc` fails with **1455 `ERROR_COMMITMENT_LIMIT`** at 496 MB committed; **engine is not killed**, stays responsive (ping and render still work); IOCP delivers `JOB_OBJECT_MSG_PROCESS_MEMORY_LIMIT` 0.2 ms after the failed allocation |
| native commit, job-wide limit 512 MB | same, message `JOB_OBJECT_MSG_JOB_MEMORY_LIMIT` |
| production default 2 GiB per process | fails at 2032 MB, same behaviour, notification at +420 ms (time to touch 2 GiB) |
| managed `byte[]` (.NET GC) | the **GC reads the job limit and sets its own hard limit** (about 72 percent): `OutOfMemoryException` at 368 MB with **no job notification at all**; engine survives |
| no limit (control) | stopped by the engine at 3 GiB |

How the broker detects it: the **IOCP notification is the only signal** for native allocations; the process is not terminated, so the broker (or watchdog) must decide to kill and respawn on `PROCESS_MEMORY_LIMIT`. A C++ engine's allocator will probably abort on allocation failure (the PDFium build here uses no PartitionAlloc), after which the broker sees process exit instead: **not measured**. The managed case shows the broker would miss a "limit hit" entirely if the engine handles OOM itself, so the engine's own OOM handler must also report to the broker.

### R5. Fonts (Q3) (`out/results/fonts.md`, images in `out/fonts/`)

Fixtures: a generated page with 13 non-embedded fonts (five standard-14, Arial, Arial,BoldItalic, TimesNewRomanPSMT, Georgia, SegoeUI, CourierNewPSMT, Symbol, Verdana) plus two lines of Shift-JIS text in non-embedded MS Mincho (`/90ms-RKSJ-H`); `hello_world.pdf` and `font_weight.pdf` from the corpus. All files reach the engine as duplicated handles. Reference A = outside sandbox with PDFium's default Windows font path.

| Config | fonts fixture: pixels differing from A / SSIM | hello_world | font_weight |
|---|---|---|---|
| A outside sandbox, default (GDI) | reference | reference | reference |
| **B AppContainer, default (GDI)** | **0 (bit-identical) / 1.0000** | **0 / 1.0000** | **0 / 1.0000** |
| G Low-IL, default | 0 / 1.0000 | 0 / 1.0000 | 0 / 1.0000 |
| C AppContainer, provider returns nothing (PDFium built-in Foxit fonts only) | 50,587 (6.54 %) / 0.9509 | 6,183 (0.97 %) / 0.9947 | 636 (0.10 %) / 0.9995 |
| D AppContainer, custom `FPDF_SYSFONTINFO` (files from `C:\Windows\Fonts`, no GDI) | 6,574 (0.85 %) / 0.9837 | **0 / 1.0000** | **0 / 1.0000** |
| E outside sandbox, same custom provider | identical to D | identical to D | identical to D |

- **GDI (PDFium's default Windows font path) works inside a zero-capability AppContainer with pixel-identical output.** `CreateCompatibleDC`, `CreateFont("Arial")`, `GetTextFace`, `GetFontData` (1,045,720 bytes) and a direct `CreateFile` on `arial.ttf` all succeed; the container can read `C:\Windows\Fonts`.
- The only sandbox setting that breaks the GDI path is **Win32k lockdown**, which is what the mitigation matrix shows the .NET engine cannot run under. **GDI behaviour under Win32k lockdown is therefore not measured** (it cannot be run with this stub); I expect GDI to fail there but that is an expectation, not evidence.
- The "no system fonts" row (C) is the damage if system fonts are unavailable and no provider exists: 6.5 percent of pixels change on the font-heavy page and non-embedded CJK is not rendered.
- **A broker-style provider is small and works.** `engine/FontProvider.cs` is about 190 lines: family and weight mapping to six TrueType files plus `msgothic.ttc`, whole-file and table-level `GetFontData`, `GetFaceName`, charset, no GDI/win32k. Rendering is bit-identical to GDI on the two corpus files and within SSIM 0.984 on the font-heavy page. The remaining 0.85 percent is mostly **CJK that the provider renders and GDI does not**: this Windows 11 box has no MS Mincho, so the default path leaves the Shift-JIS lines blank (visible in `out/fonts/fx1-A.png` vs `fx1-D.png`), while the provider maps CJK to MS Gothic. Symbol is not in the provider's table and falls back to the built-in font (12 of 13 map calls hit).
- **Provider gotchas** (each cost a crash, `0x80000003`, a PDFium CHECK): (1) `GetFontData(table = 'ttcf')` must return **0** for a plain `.ttf`; returning the whole file makes PDFium treat it as a collection and abort. (2) The header says a provider may implement only `GetFont`/`EnumFonts`, or only `MapFont`; both work, but the `MapFont` route matched GDI better (0.85 % vs 5.08 % difference). (3) The header documents `FPDF_SYSFONTINFO` version 2 ("per-request", skips `EnumFonts`, marked experimental); only version 1 was tested. (4) Exceptions in an `UnmanagedCallersOnly` callback kill the process.
- **How much work for production:** the real broker-mediated version needs the broker to enumerate fonts (DirectWrite), serve face data over the shared section (or give the engine read-only handles to font files), and a charset-aware fallback table (CJK, Arabic, Hebrew, Thai, symbols). Estimate for the C++ side: a few hundred lines of C++ for the `FPDF_SYSFONTINFO` adapter, plus the broker font service. That estimate is a guess based on this prototype, not a measurement.

### R7. Low-IL fallback (Q6)

- `CreateRestrictedToken(DISABLE_MAX_PRIVILEGE)` plus Low integrity, launched with `CreateProcessAsUser`, needs **no special privilege** for a standard (UAC-filtered admin) user, because the token is a restricted version of the caller's.
- The pipe needs a **Low mandatory label SACL** (`S:(ML;;NW;;;LW)`). `NamedPipeServerStreamAcl.Create` fails with "A required privilege is not held" (1314) because .NET asks for `ACCESS_SYSTEM_SECURITY`; a native `CreateNamedPipe` with the SD in `SECURITY_ATTRIBUTES` works.
- **A restricting-SID set that excludes the user SID does not run at all** (`0xC0000142`/`0xC0000022` for even `cmd.exe`; diagnosis in `out/results/lowildiag.txt`). Real read isolation from a restricted token would need Chromium's two-token (initial then lockdown) scheme: **not attempted**.
- The .NET **framework-dependent apphost fails under Low IL** (`0x80008085`, "Failed to resolve full path of the current executable"); self-contained works. **Separately, an inheritable AppContainer ACE on the engine directory makes the Low-IL apphost fail too**, reproduced both ways: the same dir without the ACE works, with `icacls ... (OI)(CI)(RX)` fails, with a non-inherited `(RX)` on the dir only works. Not root-caused. The spike uses a separate ACL-free copy (`engine-sc-low`).
- Result: Low-IL is a **materially weaker** sandbox (see R2). It only passes the write-isolation tests. It does not meet the spec's bar of "every negative test denied" even with the same extras, because reads, network, clipboard and cross-process opens stay open.

## Surprises

1. **AppContainer worked on the first try, with GDI fonts pixel-identical.** The predicted font blocker did not materialise. The real font risk is Win32k lockdown, not AppContainer.
2. **`CreateProcess` is not blocked by an AppContainer.** `cmd.exe` launched fine from the zero-capability container. The child-process policy is mandatory, not optional.
3. **A console-subsystem engine plus child-process or Win32k policies fails with `0xC0000142`** because of `conhost.exe`. Detaching the console is a hard requirement for any console-subsystem engine; a native cmd.exe/hostname.exe ran under Win32k lockdown, the .NET apphost cannot (it statically imports user32/shell32/gdi32).
4. **Creation-time "Microsoft-signed only" cannot work for Quire's own DLLs** (not Microsoft- or Store-signed). The runtime variant after loading does work and gives a 577 on later unsigned loads. The master prompt's wording ("except Quire's own signed DLLs") has no direct Win32 flag.
5. **Synchronous named-pipe handles deadlock a reader/writer thread pair** on the same handle. Use overlapped (async) pipes on both ends, or a single thread.
6. **PDFium abort on a legitimate-looking font provider**: returning the whole file for `ttcf` crashes PDFium with `STATUS_BREAKPOINT`. No error is reported anywhere except the exit code.
7. **A `.NET` GC honours the job memory limit by itself** (75 percent hard limit). The broker gets no notification when a managed engine hits it.
8. `FPDF_FILEACCESS.m_FileLen` is 32-bit on Windows (4 GiB cap).
9. **Odd Low-IL behaviours:** the apphost failure with an inheritable AppContainer ACE (above) and the Low-IL fdd apphost failure.
10. A same-user medium-IL process can connect to the pipe; the DACL cannot prevent that. The connected-client pid check covers a squatter that wins the race (verified to report the right pid).
11. **A dry run at 100 percent system CPU gave 13 ms Ping medians.** CPU contention from other builds can swamp IPC latency measurements; the final runs were taken at 18 to 34 percent and repeated at normal and high priority with the same result.

## Recommendation (input to ADR-0004 and ADR-0005)

**ADR-0004: process model and sandbox**

1. **AppContainer with zero capabilities is viable and should be the primary sandbox.** It denied every negative test in ac-hardened and costs nothing measurable in latency or spawn time. Low-IL is an explicit last resort and does not meet the §5.3 intent (user data readable, network open, other processes openable); document that in the ADR rather than treating it as an equal alternative.
2. **Mandatory creation-time attributes:** `SECURITY_CAPABILITIES` (0 caps), `HANDLE_LIST` (file, section; add stderr/log handle if wanted), `JOB_LIST` (atomic job assignment, worked on this OS), `CHILD_PROCESS_POLICY = RESTRICTED`, DEP/ASLR/strict-handle/extension-point/image-load/CFG, CET (compat), and job limits (kill-on-close, per-process 2 GB, UI limits). **Start the engine detached (no console).**
3. **Signature policy: apply at runtime**, after PDFium and the runtime have loaded, not at creation. State this in the ADR as the interpretation of §5.3. Re-test this on the C++ engine with its real DLL load pattern.
4. **Win32k lockdown and prohibit-dynamic-code (C++ re-test in S3b):** dynamic-code prohibition **works** with non-V8 PDFium; Win32k lockdown **fails with the prebuilt `pdfium.dll`** and needs a custom PDFium build. PDFium without V8 has no JIT, so dynamic-code prohibition is plausible; Win32k lockdown will force the `FPDF_SYSFONTINFO` provider (below) and no static user32/gdi32/shell32 imports.
5. **ACLs:** grant the container read+execute on the engine directory only (package directory in production). Do not rely on it for the .NET runtime directory if a managed engine is ever used. No ACL changes in Program Files were needed.
6. **Memory limit:** the broker must treat `JOB_OBJECT_MSG_PROCESS_MEMORY_LIMIT` as a trigger to kill and respawn; the process is not terminated by the OS and the engine's own OOM handler must also report (managed engines can swallow the OOM).
7. **Broker-owned I/O is confirmed:** `HANDLE_LIST` for the first document, `DuplicateHandle` for later ones. Fix the 4 GiB `FPDF_FILEACCESS` limit in ADR-0002/0005 (use `FPDF_LoadMemDocument64` over a mapped view if large files are in scope).
8. **Fonts:** keep PDFium's default GDI path for the first sandboxed build (it is bit-identical in the AppContainer) and **plan the broker font provider as the Win32k-lockdown enabler**, not as an AppContainer necessity. A working prototype exists (`engine/FontProvider.cs`), including CJK that GDI misses on a machine without those fonts.

**ADR-0005: IPC transport and serialisation**

1. Named pipe with random 128-bit name, native `CreateNamedPipe` (first instance, reject remote clients), DACL = user + engine's AppContainer SID, plus a **connected-client-pid check**, as implemented. **Overlapped (async) pipe handles on both ends** (or one thread per direction on separate handles).
2. Budget evidence: Ping p99 about 0.1 ms on DEV; RenderTile transport overhead p99 about 0.25 ms. The 1 ms gate has an order of magnitude of headroom on this machine; R1/R2 still need the run.
3. **Serialisation: either works on this evidence.** MessagePack-CSharp 3.1.12 with its built-in source generator works and decodes a 400 KB message in about 0.4 ms p50; a flat custom reader is 2.5 to 4 times faster on decode. Given the §5.4 requirement to fuzz both decoders and the C++ side is not in this spike, I recommend the ADR keep MessagePack for control messages **only if** a C++ MessagePack library with a bounds-checked reader is acceptable; otherwise a fixed-layout binary protocol is simpler to fuzz. This is Opus's call (see open questions).
4. Large payloads (`GetCharBoxes` at 400 KB on a very dense page) should go through the slot ring too, not the control pipe. Tile slots work: zero-copy render into the section, broker reads read-only.
5. Hello, Ping (I/O thread) and engine-thread messages should be separate paths so heartbeat still works during a render: confirmed workable (`Ping` vs `PingEngine`).

**Provisional GO for AppContainer with zero capabilities as the engine sandbox**, subject to these conditions: (a) ~~the three items marked "not measured for C++" re-tested~~ **done in S3b** (dynamic code pass, runtime signature pass, Win32k fail with prebuilt PDFium); (b) the launcher is re-run from a packaged MSIX (S6.3); (c) timing gates are re-run on R1 and R2.

## Open questions for Opus

1. **Signature-policy wording (§5.3).** "Block non-Microsoft-signed DLLs (except Quire's own signed DLLs)" is only achievable as a runtime lock after loading, not as a creation flag. Accept the runtime interpretation in ADR-0004? It means the engine must pre-load every DLL it will ever need.
2. **Win32k lockdown vs GDI fonts.** If the C++ engine will be Win32k-locked, the font provider becomes mandatory and the broker needs a font service. Do we want that in M2 scope or only if the lockdown test passes first?
3. **MessagePack vs a fixed binary protocol** (see ADR-0005 recommendation 3): which one do you want fuzzed, given the C++ side?
4. **Low-IL**: keep only as a documented last resort, or drop it from the plan? It does not meet the stated protection and it breaks the .NET apphost in two ways.
5. **Packaged behaviour** is not measured: do you want S6.3 to own the repeat of this launcher inside the MSIX, including the ACL on the package directory?
6. **The `FPDF_SYSFONTINFO` version 2 ("per-request, experimental")** in the pinned header could replace `EnumFonts` entirely. Worth testing in S1/ADR-0002 given the weekly PDFium bump policy?
7. The unexplained items (restart bimodality, 66 ms Hello build outside the sandbox, one 5 to 7 ms PingEngine outlier per 10,000, the Low-IL apphost/AppContainer-ACE interaction): ignore for now or ask for follow-up?

### S3b method

System CPU during the timing runs was 18 to 29 percent (sampler), with 7 to 16 percent measured just before; the machine was quieter than during the .NET runs but the other agents were still active. - The self-signing test used a throw-away 3072-bit RSA certificate created in memory and exported to `out/selfsigned/test.pfx` (deleted afterwards), signed with `signtool` from the SDK. **Nothing was installed in any certificate store.**

### S3b results

**Controls (all pass):** the C++ engine in the zero-capability AppContainer starts in about 10 ms, opens the document from the inherited handle, renders into the section (1,305 ink pixels on `hello_world.pdf`, same as the .NET stub), the GDI probe is fully OK, and the fonts fixture renders **bit-identical** to the unsandboxed C++ reference (SSIM 1.0000, same as .NET). **Q2. Options for production, in order of how much they need:

1. **Runtime lock after load (works today, no certificate):** load PDFium and every other DLL the engine will ever need, then call `SetProcessMitigationPolicy(ProcessSignaturePolicy, MicrosoftSignedOnly)`. Anything unsigned or non-Microsoft loaded afterwards fails with 577; late loads of Microsoft-signed system DLLs keep working. This blocks a planted DLL loaded after the lock, not code already loaded.
2. **Creation-time flag with the Store allowance:** needs binaries carrying a **Microsoft Store signature**. A self-signed signature is not accepted (shown above). A CA-trusted Quire signature is **not tested**, but the documented meaning of the flag is "Microsoft or Store", not "any trusted publisher". Whether the files inside a Store-distributed MSIX qualify (the Store signs the package and a catalog, not each DLL) is **not tested and unclear from the docs**. This is the "MSIX package signature path" question and needs a test in S6.3 with a real Store-signed package.
3. **Code Integrity policy (WDAC) allowing the Quire publisher certificate:** it is machine policy, outside what a per-user app can set; not suitable for a consumer app. Not tested.
4. **Static-link PDFium into the engine exe** so no separate PDFium DLL is loaded: the delay-load run showed the creation flag accepts the unsigned exe itself (it applies to DLL loads after the exe is mapped), so "creation flag plus static PDFium plus system DLLs only" is a possible route. **Not tested** (needs a PDFium static library, which is S1).

- Ping RTT (hardened AppContainer, n = 10,000, µs): run 1 p50 10.3, p95 23.0, p99 33.9, max 317.3; run 2 p50 10.2, p95 15.2, p99 24.3, max 537.2; **0 samples above 1 ms**. PingEngine (through the work queue): p50 16.4 / 15.4, p99 35.4 / 35.5, max 264.5 / 256.7. About 3 times lower than the .NET stub (p99 86 to 122 µs).
- RenderTile 512 x 512, hardened AppContainer, n = 1,000: RTT p50 0.78 ms @1x and 0.57 ms @2x (run 1); engine 0.75 and 0.54 ms; **transport overhead p50 0.029 ms, p99 0.118 ms @1x (p99 0.075 ms @2x)**, about 3 times lower than .NET (p50 0.079, p99 0.247). It is the same simple fixture as before, so render time is not representative of heavy pages.

### What carries over from the .NET stub, and what changed

- **Confirmed unchanged:** AppContainer launch, handle-list inheritance, `DuplicateHandle` into the container, pipe DACL behaviour, GDI font parity (bit-identical). The C++ engine passes the same positive controls. I did **not** re-run the full negative-access suite or the Job memory-limit test on the C++ engine (that code lives in the .NET stub); those OS-level results do not depend on the managed runtime, but they are **not re-measured for C++**.
- **Changed by S3b:** (1) Win32k lockdown is **a PDFium-build problem, not a .NET problem**: the C++ engine fails too. (2) Dynamic-code prohibition is **viable** for non-V8 PDFium. (3) The creation-time signature flag is **not viable** even with an Authenticode-signed file; the runtime lock is. (4) Spawn time is about 10 ms rather than 55 ms, so "spawn plus open under 500 ms" has more than 40 times headroom in this configuration (DEV class; R1 not run). (5) CET strict mode works with this PDFium build.

### S3b: effects on the recommendation (ADR-0004 / ADR-0005)

1. **Mitigation set for the C++ engine, tested working together:** AppContainer (0 caps) + child-process policy + DEP + ASLR (bottom-up, high-entropy, force-relocate) + strict handle checks + extension-point disable + image-load restrictions + CFG + **prohibit dynamic code** + CET (compat or strict) + job UI limits, then runtime `MicrosoftSignedOnly` after PDFium is loaded. Start the engine **detached**.
2. **Win32k lockdown:** drop it from the M1/M2 baseline while using the prebuilt `pdfium.dll`. Keep it as a goal contingent on S1 producing a PDFium build that initialises under lockdown; the broker font provider is already prototyped (SSIM 0.98 vs GDI, CJK excepted). **Next concrete step (small):** find what in `pdfium.dll`'s init fails (loader trace or a debug build) and whether a GN flag removes it.
3. **Signature policy:** use the runtime lock now; decide on a Store-signature route after the S6.3 test. Do not plan on a creation-time flag with a publisher certificate.
4. **ADR-0005 numbers:** with the C++ engine Ping p99 is about 25 to 35 µs and the RenderTile transport overhead p99 about 0.12 ms on DEV, so the 1 ms gate has about 30 times headroom for Ping.

### S3b: Go / No-go change

The verdict stays **provisional GO for the zero-capability AppContainer** and now covers the C++ engine for everything except Win32k lockdown. Updated conditions:

- (a) Win32k lockdown, dynamic code and the runtime signature policy re-tested on the C++ engine: **done**. Dynamic code **pass**, runtime signature **pass**, Win32k **fail with the prebuilt PDFium** (carry into S1/ADR-0002 as a build requirement; it does not block the sandbox itself).
- (b) Launcher re-run from a packaged MSIX (S6.3): **still open**, and it now also owns the Store-signature question.
- (c) R1/R2 timing re-run: **still open**.
- (d) Negative-access suite and memory-limit test on the C++ engine: **not re-run**.

### S3b: open questions for Opus

1. Is Win32k lockdown worth a PDFium build effort (S1 scope), given that dynamic-code prohibition, the child-process policy, the runtime signature lock, the AppContainer and the job already close most of what lockdown would add?
2. The 8 MB frame cap rejected `msgothic.ttc` (8.6 MB). Should the font service use the shared section or chunking, and should the cap stay at 8 MB for ordinary messages?
3. The 110 to 120 ms restart outlier in the hardened C++ set (and the similar one in .NET): leave unexplained until R1, or bisect now?
4. The Store-signature path (`ALLOW_STORE` plus an MSIX from the Store) cannot be tested here: should S6.3 test it, or do we accept the runtime lock as the design?
