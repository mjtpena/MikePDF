## Questions

1. Does WinUI 3 on the pinned SDK expose `ITextProvider`, `ITextProvider2` and `ITextRangeProvider` so that a custom `FrameworkElementAutomationPeer` written in C# can implement them? **This is the core feasibility question.**
2. Can text ranges map onto PDFium character data, with `ExpandToEnclosingUnit`, `Move` and `MoveEndpointByUnit` for Character, Word, Line, Paragraph, Page and Document, and with `GetBoundingRectangles` correct on all four page rotations, a non-zero CropBox origin and `/Rotate`?
3. Do selection-changed and text-changed events reach a UIA client? (Narrator and NVDA specifically: not measured.)
4. Reading order: does the structure tree drive it for tagged files, and does a heuristic work for an untagged two-column page?
5. Extra questions that came up: which coordinate units does the XAML wrapper expect from a text provider; which thread do UIA calls arrive on; is TextPattern2 exposed; does the model survive files we did not write.

### Fixtures: how each was obtained

The PDFium corpus (`pdfium-resources`) has `tagged_*.pdf` files but they are single-line "Sample Text" documents, none has multi-line paragraphs, none has a structure tree whose order differs from content order, and `tagged_nested.pdf` is deliberately malformed marked content. They cannot answer the reading-order question. PDFium's edit API cannot write a structure tree either. So all four fixtures are **written by hand** by `FixtureGenerator` (raw PDF objects plus an xref writer), and are committed in `spikes/S7/fixtures/`:

| Id | File | What it exercises |
|---|---|---|
| a | `a-tagged-single-column.pdf` | `StructTreeRoot`, `/MarkInfo`, MCIDs. **Content stream order is deliberately wrong**: footer artifact, paragraph 2, heading, paragraph 1. The structure tree says H1, P, P. |
| b | `b-untagged-two-column.pdf` | Title spanning both columns, two columns of 10 lines at 10 pt with a paragraph break in each, **content stream emitted row by row** (L1, R1, L2, R2, ...). |
| c | `c-rotate90-cropbox.pdf` | `/Rotate 90`, `/CropBox [100 150 500 650]` (non-zero origin), text authored so that it is upright after the page rotation (`Tm = [0 1 -1 0 x y]`), "TOP LEFT" and "BOTTOM RIGHT" corner markers, and one line **outside** the CropBox that must not be read. |
| d | `d-ligatures-hyphenation.pdf` | Standard-encoding `fi` and `fl` ligature glyphs (codes 0xAE, 0xAF), a hard hyphen ("well-known"), and two line-end hyphenations ("exam-" / "ple", "sec-" / "ond"). |

Expected results for every fixture are hand-written from how the file was authored (`A11yTest/Expectations.cs`), not derived from the model under test.

### Text model (the part Opus should review hardest)

- **Atoms.** The accessible text is a list of atoms in reading order. An atom is one Unicode text element with a rectangle in "base page space" (page `/Rotate` applied, view rotation 0, origin top-left, points). The model also inserts synthetic atoms: a single space between the lines of a paragraph, and `\n` between paragraphs. Synthetic atoms have no rectangle. A UIA range is `[start, end)` in atom indices.
- **Boxes.** Rectangles come from `FPDFText_GetLooseCharBox` (font-metric height, so highlights tile into contiguous line bands). `FPDFText_GetCharBox` (tight glyph box) gives zero-height boxes for spaces and ragged heights for letters.
- **Filtering.** PDFium's generated CR/LF are dropped (replaced by the model's own separators). Characters whose box centre is outside the visible CropBox are dropped. Soft hyphen and zero-width characters are dropped. U+FB00 to U+FB06 are expanded (NFKC restricted to those code points; a blanket NFKC would also rewrite superscripts and full-width forms).
- **Ligature boxes.** PDFium already splits a `fi` glyph into two characters but gives **both the same box**. The model splits that box into equal horizontal shares so per-character rectangles tile the glyph.
- **Hyphenation.** PDFium marks a line-end hyphen with U+0002 and `FPDFText_IsHyphen = 1`, and emits no CR/LF after it. The model removes the hyphen from the text, extends the previous atom's rectangle over it, and adds no separator, so "example" is one Word that spans two lines (two rectangles) while the Line unit still breaks between "exam" and "ple".
- **Reading order, tagged pages.** Walk the structure tree (`FPDF_StructTree_GetForPage`, `FPDF_StructElement_*`) depth first. A block is a block-level element (P, H1..H6, LI, LBody, Lbl, TD, TH, Caption, Figure, ...) and collects the MCIDs beneath it, read through `FPDF_StructElement_GetChildMarkedContentID` (this also handles the `/K << /Type /MCR /MCID n >>` form). MCID to characters: `FPDFText_GetTextObject(char)` then `FPDFPageObj_GetMark` / `FPDFPageObjMark_GetParamIntValue("MCID")` on that text object. Characters that no block claims (artifacts) are ordered with the untagged heuristic and appended at the end, flagged `Artifact`.
- **Reading order, untagged pages (documented heuristic).** Recursive XY-cut on glyph rectangles in base page space:
  1. Find the widest empty vertical band of at least **1.0 em** that no glyph crosses: cut, recurse left then right.
  2. Otherwise find the widest empty horizontal band of at least `max(0.5 em, min(1.5 x median inter-line gap, 3 em))`: cut, recurse top then bottom.
  3. Otherwise the region is a leaf: cluster into lines by vertical centre (tolerance half a line height), order each line left to right, and start a new paragraph where the line pitch exceeds 1.45 x the median pitch.
  Vertical cuts are tried first so a two-column body is not sliced row by row; a full-width title or footer blocks a page-wide vertical cut and falls through to rule 2.
  Not handled: right-to-left, vertical writing, rotated text runs inside an upright page, tables (read in cut order, not row order), CJK word breaking.
- **Units.** Character: every atom. Word: whitespace-delimited, trailing whitespace belongs to the word (as in the Win32 edit control), punctuation stays attached. Line: visual line, from the geometry. Paragraph: tagged block, or the heuristic. Format: run of equal font size. Page and Document: the whole text (single page).
- **Move / MoveEndpointByUnit.** `Move` on a non-degenerate range first normalises to the unit at Start, then steps whole units, never stepping onto the end-of-document sentinel (a further `Move` at the last unit returns 0). `Move` on a degenerate range moves the point. `MoveEndpointByUnit` moves one endpoint across unit boundaries (a position strictly inside a unit counts the boundary it reaches as one move), and the other endpoint follows if they would cross. These are my reading of the UIA documentation plus the Win32 edit control's behaviour; the docs are silent on some corners, so the choices are listed here.

### Coordinates

`PageGeometry` converts user space to page space for any `/Rotate`, CropBox origin and view rotation, and is **checked against `FPDF_PageToDevice` and `FPDF_DeviceToPage`** (see Results). The UIA test then computes the expected screen rectangle of every character independently (PDFium loose box, `PageGeometry`, zoom, DPI scale, element origin from UIA) and compares it with what `GetBoundingRectangles` returns through UIA.

## Surprises

1. **The coordinate contract for text ranges is not the UIA one.** Native UIA says `GetBoundingRectangles` returns screen pixels and `RangeFromPoint` receives screen pixels. My first implementation did that (`ClientToScreen` plus the DPI scale). The UIA client then saw every rectangle displaced by exactly the window's client origin (for the first character, expected (184, 255.4), got (296, 390); the page element itself was at (112, 183) and the app's client origin turned out to be (112, 134.6)). The XAML wrapper adds the client origin and applies the DPI scale itself. **A WinUI 3 text provider must work in DIPs relative to the XAML root (window content)**, and `RangeFromPoint` hands you root-relative DIPs (log: UIA client point converted to `(74,132)` for a point inside the first glyph). Fixing it made all per-character checks pass. At 100% scale this cannot distinguish "root-relative DIPs" from "root-relative pixels"; I inferred DIPs from the framework's documented behaviour and the fact that it adds the client origin, not from a measurement at 150%. That needs a non-100% machine (Open questions).
2. **`new XamlControlsResources()` in a code-only app kills the process** at start-up with a stowed exception (`combase.dll`, 0x8000FFFF, process exit code -1073741189), before `OnLaunched`. I removed it, so the toolbar uses the framework's base control styles. A real `App.xaml` may behave differently; S6's `HelloQuire` uses XAML. Does not affect the Text pattern.
3. **PDFium's text order is not reading order in any of the three non-trivial cases** (R2): content order for the tagged file, row-interleaved merged lines for the two-column file, and content order (corner markers before the body, hidden line included) for the `/Rotate 90` file. In an earlier draft of fixture c, whose text was horizontal in user space (so it showed rotated on the page), PDFium returned the four body lines in reverse order; I discarded that draft when I re-authored the text to be upright after rotation and did not re-verify the reversal with the final code, so treat it as an anecdote. Only the character boxes, the Unicode, and the MCIDs are trustworthy inputs.
4. **PDFium expands ligatures itself but leaves both characters with the same box**, so naive per-character rectangles overlap exactly. U+FB01 never reached the model with this fixture; the NFKC expansion for U+FB00 to U+FB06 stays in as a guard that was not exercised.
5. **PDFium hyphenation handling is good and useful**: a line-end hyphen becomes U+0002 with `FPDFText_IsHyphen = 1` and no CR/LF follows; a mid-line "well-known" hyphen is an ordinary U+002D with `IsHyphen = 0`.
6. **`FPDFText_GetText` and `CountChars` include text outside the CropBox** (the header says so). The hidden line in fixture c is returned; the model filters it by box centre.
7. **Tight char boxes are not usable for highlight rectangles**: spaces get zero height, letter heights vary per glyph. `FPDFText_GetLooseCharBox` (Experimental) gives consistent line bands.
8. **Only `Control`s take keyboard focus in WinUI.** The first design (a `Grid` subclass) could not be focused, which a screen reader caret needs. `ContentControl` fixes that; the peer returns no children so the internal `Image` and overlay are not exposed.
9. **The managed UIA client (`System.Windows.Automation`) cannot express TextPattern2** (`AutomationProperty.LookupById(30119)` returns null). I used a native `IUIAutomation` client via CsWin32 for that check.
10. Provider calls are marshalled to the UI thread by the XAML wrapper (good for a single-threaded model, but it means long text operations block the UI; see Recommendation).
11. The Python and shell tooling I used for edits mangled backslashes (`\n`) in C# source twice. No effect on the results; mentioned only because it cost time.

## Recommendation

### Input to ADR-0006 (surface choice must support UIA)

- **WinUI 3 on Windows App SDK 2.5.1 can host an accessible custom-rendered page.** Implement `ITextProvider`/`ITextProvider2` on a `FrameworkElementAutomationPeer` and return it from `GetPatternCore(Text)` and `(Text2)`. The Win32 child HWND fallback is not needed on this evidence.
- **UIA does not constrain the choice between Win2D and Composition**, provided the page surface is a **XAML `Control` that Quire owns and that owns the peer** (a `ContentControl`-derived `PageSurface`) with the presenter (Win2D `CanvasVirtualControl`, `SwapChainPanel`, or a Composition visual) as its content and **hidden from UIA** (`GetChildrenCore` returns empty). This was only demonstrated with an `Image` as the content; it still has to be shown with the S2 presenters.
- Make the "accessible text model" independent of the presenter and of tiles. It needs only page boxes, character data and the structure tree. It must not depend on whether pixels come from Win2D or Composition.

### Design of `Quire.Accessibility`

1. **Pure core, no WinUI references**: `TextModel`, `TextRange`, unit boundaries, reading order, geometry. This is `S7.Core.Text` and `S7.Core.Geometry` nearly as written. It is unit-testable headless, which is how 94 of the 345 checks here run.
2. **Thin WinUI adapter in `Quire.App`**: peer + `ITextRangeProvider` wrapper, about 190 lines (`PageSurfaceAutomationPeer.cs`). The adapter converts to and from XAML-root DIPs and raises events.
3. **Engine contract** (replaces the in-process stand-in): `GetPageText(page)` returns the `PageTextData` shape: per character `{index, UTF-16 text, loose box (4 numbers), generated, hyphen, MCID, font size}`, page `{media box, crop box, /Rotate}`, and struct blocks `{type, MCIDs, alt, actualText}`. Everything is plain data. My size estimate (not measured here, for S3 to confirm): about 30 bytes per character before MessagePack, so a dense page of 5,000 characters is about 150 KB. PDFium functions used, with the **Experimental** ones marked because they are a pinning risk for ADR-0002: `FPDFText_GetTextObject`*, `FPDFText_IsGenerated`*, `FPDFText_IsHyphen`*, `FPDFText_GetLooseCharBox`*, `FPDFText_GetCharAngle`* (dumped only), `FPDFPageObj_CountMarks`*, `FPDFPageObj_GetMark`*, `FPDFPageObjMark_GetParamIntValue`*, `FPDF_GetPageBoundingBox`*, `FPDF_GetPageWidthF/HeightF`*, `FPDF_StructElement_GetChildMarkedContentID`*, `FPDF_StructElement_GetActualText`* (called, unused); stable: `FPDFText_LoadPage/CountChars/GetUnicode/GetFontSize/GetCharBox/GetText`, `FPDFPage_GetMediaBox/CropBox/GetRotation`, `FPDF_StructTree_GetForPage`, `FPDF_StructElement_GetType/GetChildAtIndex/CountChildren/GetAltText`. S1 should confirm each against its API checklist.
4. **Compute the model in the app process from engine data, once per page, cache it** (the sweep's p95 of 2.9 ms per page suggests this is cheap; a dense page needs a real measurement). Selection state lives in the app layer; the provider only reads and writes it, so keyboard, mouse and UIA selection share one source of truth.
5. **Rotation never changes the text model.** Build the model in base page space (page `/Rotate` applied) and rotate rectangles for the view. Reading order must not change when the user rotates the view, and here it does not.
6. **Prefer the struct tree, fall back to the heuristic, and announce the fallback.** Master prompt 10.3 wants "This document is not tagged" announced once; use `AutomationPeer.RaiseNotificationEvent` (not tested here). Hide artifacts from the reading flow or keep them last (the spike keeps them last, flagged).
7. **Provider methods run on the UI thread**, so keep every range operation O(log n) or O(units); build and cache boundary arrays eagerly (done here) and keep rectangle building to the requested range.
8. **Test strategy**: keep this spike's `uia-tests` as the golden end-to-end test for CI (needs an interactive desktop session), keep the model tests as the fast headless layer, and add the manual script per milestone (master prompt 12.7).

## Go / No-go

**Go, provisional**, for the question S7 asks of ADR-0006: *WinUI 3 does allow implementing the Text pattern*, rectangles are correct on all four rotations including a `/Rotate 90` page with a non-zero CropBox origin, reading order follows the structure tree for tagged files and a documented heuristic for the untagged two-column fixture, and selection and text-changed events reach a UIA client.

It is **provisional, not a pass of the spike-plan gate**, because the plan's criteria include Narrator reading each fixture by character, word and line, and Accessibility Insights FastPass with zero failures. Both are **not measured (manual pass pending)**, and so is NVDA. Display scales other than 100% and the Win2D/Composition presenters are also unmeasured. If the Narrator pass finds problems, the likely causes are in the model (word and line conventions, artifacts last) and the adapter, not in feasibility.

## Open questions for Opus

1. **Gate decision.** Is a provisional Go enough to write ADR-0006 now, with the Narrator/NVDA/FastPass pass tracked as an M0 exit item? Who runs `narrator-script.md`, and on which Windows build?
2. **Non-100% DPI.** I could not test 125% to 200% on this machine. The wrapper's handling of root-relative DIPs vs DPI scale is inferred (Surprise 1). R3 (4K at 150% and 200%) is the natural place; should that run be added to S2 or kept in S7?
3. **Multi-page and virtualisation.** A 2,000-page document cannot expose one document range containing all text. Options: one UIA Document element per visible page (children of a scroll container), or one element with lazily extended ranges and a Page unit that maps to page boundaries. Which does ADR-0006 want? The spike has one page only.
4. **Native AOT.** The peer implements WinRT interfaces in managed code (`ITextProvider`, `ITextRangeProvider`). S6 owns AOT vs R2R; please have S6 (or a follow-up here) build this exact peer under AOT/ReadyToRun and re-run `uia-tests`. I only tested JIT, and CsWinRT's handling of managed implementations of WinRT interfaces under trimming/AOT is the sort of thing that fails late.
5. **Line text and hyphenation.** I drop the hyphen at a hyphenated line end and join the word across two lines. A line-by-line read says "exam" then "ple". The alternative is to keep a visible hyphen in the Line text but not the Word text, which cannot be done with one text string per position. Which behaviour do we want, and does the user-facing spec need a setting?
6. **Word unit.** Whitespace-delimited words are wrong for CJK and for punctuation-heavy text. Do we adopt a UAX #29 word-break (ICU, already in PDFium's tree, or `System.Globalization` text elements) for the Word unit? That is a new-dependency question.
7. **Artifacts.** Headers, footers and page numbers are currently read last. Hiding them from the text range makes them unselectable. Preferred: read last, or hide, or read in position?
8. **Reading-order accuracy.** The XY-cut heuristic is validated on one synthetic page and an invariant sweep. It needs the real corpus from ADR-0010 (multi-column papers, tables, sidebars) before anyone relies on its thresholds (1.0 em, 0.5 em, 1.5 x median gap, 1.45 x median pitch).
9. **Dependencies.** None added to production. Spike-only: `Microsoft.WindowsAppSDK` 2.5.1 and `Microsoft.Windows.SDK.BuildTools` 10.0.26100.7705 (Microsoft licence terms; the former ships a `license.txt`), `Microsoft.Windows.CsWin32` 0.3.367 (MIT, used only by `UiaNative`), WPF `UIAutomationClient` from the .NET Windows Desktop runtime (MIT, test client only). Win2D, MessagePack and others were not used.
10. **Pass criteria wording.** The plan says "bounding rectangles land on the glyphs for all four rotations (screenshot overlay)". I did that, and I also compare against an independent calculation through UIA. If you want only the screenshot standard, the extra tests can be dropped; if you want both in CI, `uia-tests` needs a desktop session.
