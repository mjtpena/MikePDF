# S5: Ink latency (PARTIAL: S5.1 API inventory only)

- Status: **Partial.** Only task S5.1 (API inventory, desk research plus compile and runtime probe) was done. The latency, pressure and palm-rejection measurements are **not measured**: **blocked: needs Surface Pro + pen + 240 fps camera**.
- Date: 2026-10-27
- Author: Sonnet (implementation role). Reviewer: Opus.
- Machine: DEV, Intel Core Ultra 9 275HX, 64 GB, RTX 5080 laptop + Intel iGPU, Windows 11 Home 26H2 build 26300.9711, no pen digitiser. This is not the SURF device.
- Versions used: Windows App SDK **2.5.1** (WinUI 2.3.9, InteractiveExperiences 2.1.9, AI 2.5.5), Win2D **1.4.0**, .NET SDK 10.0.300 (ADR-0001 pins 10.0.403; see S6 report), Windows SDK 10.0.26100.
- Code: `spikes/S5/InkProbe/InkProbe.cs` (linked into the S6 app `spikes/S6/HelloQuire`), `spikes/S5/WinmdDump/` (winmd lister). Raw winmd dump: `spikes/S5/out/winmd-ink.txt` (gitignored; the relevant excerpts are quoted below).

## Questions

1. Which ink APIs exist in WinUI 3 on the pinned Windows App SDK? Is there an `InkCanvas`?
2. Do `Microsoft.UI.Input` pointer properties give pressure, tilt, barrel button and eraser? Is `GetIntermediatePoints` there? Is there OS prediction?
3. Can we get DirectComposition delegated ink (`IDCompositionInkTrailDevice`) from WinUI 3?
4. Which parts of the old UWP ink stack still work headless in a WinUI 3 process (for smoothing, stroke data, recognition)?
5. (Not answerable here) pen-to-pixel latency for candidates (a) native, (b) custom Win2D pipeline, (c) b plus delegated ink. Pressure fidelity. Palm rejection.

## Method

- **Metadata inventory.** I wrote `WinmdDump`, a 40-line `System.Reflection.Metadata` tool that lists public types and members from `.winmd` files. I ran it over the 2.5.1 package set (`Microsoft.UI.winmd` from InteractiveExperiences 2.1.9, `Microsoft.UI.Xaml.winmd` and `Microsoft.UI.Text.winmd` from WinUI 2.3.9, and every other `*.winmd` shipped in the 2.x component packages) with regexes for `Ink|Inking|InkCanvas|InkPresenter|DelegatedInk|Pointer|Pen|Predict`. It also ran over `Windows.winmd` of SDK 26100 for the legacy UWP ink types.
- **Compile probe.** `InkProbe.cs` uses each API by name. The project compiles against the pinned SDK, so a compiled call is proof the API exists. A compile error is recorded as evidence of absence.
- **Runtime probe (no pen).** The probe builds an `InkStroke` headless, renders it through Win2D, and calls the real `dcomp.dll` for a delegated ink trail. It ran in unpackaged and packaged x64 builds and in the Native AOT x64 build.
- **Docs.** `dcomp.h` from the Windows SDK 26100 (interfaces and IIDs). Microsoft Learn pages were checked only where stated.

## Results

### 1. WinUI 3 / WinAppSDK 2.5.1 has no ink control or ink presenter

| Looked for | Result | Evidence |
|---|---|---|
| `InkCanvas`, `InkToolbar`, `InkPresenter`, any `Microsoft.UI.Input.Inking`, `Microsoft.UI.Xaml.Controls.Ink*` | **Absent.** | `winmd-ink.txt`: the "any winmd in any WindowsAppSDK 2.x pkg mentioning Ink" section is empty. |
| Same names in `Windows.winmd` (UWP) | Present as `Windows.UI.Xaml.Controls.InkCanvas`, `InkToolbar*` (UWP XAML) and `Windows.UI.Input.Inking.InkPresenter`. | `winmd-ink.txt` last section. In the UWP model `InkPresenter` is obtained from `InkCanvas.InkPresenter` (UWP XAML) and the independent-input path needs a `CoreWindow`. I did not try to instantiate it. My conclusion that it is **not usable from a WinUI 3 desktop app** rests on the absence of any WinUI 3 hosting API in the 2.5.1 metadata, not on a runtime failure. |
| `DelegatedInk` in any WinAppSDK winmd | **Absent.** | same dump |
| Win2D `CanvasDrawingSession.DrawInk` | **Absent in Win2D 1.4.0 (WinUI build).** Compile error `CS1061: 'CanvasDrawingSession' does not contain a definition for 'DrawInk'`. The UWP Win2D had it. `Microsoft.Graphics.Canvas.winmd` has no string "Ink". | build log |

Conclusion for candidate (a): "whatever WinUI offers natively" is **nothing at control level**. There is no drop-in ink canvas in 2.5.1. ADR-0007 should treat the pipeline as custom (candidates b and c).

### 2. Pointer and pen data in `Microsoft.UI.Input` / `Microsoft.UI.Xaml.Input`

All of these compile (`InkProbe.DescribePointer`):

| Need | API | Present |
|---|---|---|
| Pressure | `PointerPointProperties.Pressure` (float 0..1) | yes |
| Tilt | `XTilt`, `YTilt` | yes |
| Rotation of the pen about its axis | `Twist` | yes |
| Azimuth-like orientation | `Orientation` | yes |
| Barrel button | `IsBarrelButtonPressed` | yes (one barrel button only, no separate "button 2" flag) |
| Eraser end / inverted | `IsEraser`, `IsInverted` | yes (both) |
| Hover | `IsInRange` (and `IsInContact` on `PointerPoint`) | yes |
| Contact area, palm hint | `ContactRect`, `TouchConfidence` | yes (`TouchConfidence` is the touch palm-rejection hint) |
| Update kind | `PointerUpdateKind` | yes |
| Pen hover height | `ZDistance` | **no** (not on `PointerPointProperties` in this SDK) |
| Coalesced high-rate samples | `PointerRoutedEventArgs.GetIntermediatePoints(UIElement)` and `Microsoft.UI.Input.PointerEventArgs.GetIntermediatePoints()`, `GetIntermediateTransformedPoints()` | yes |
| OS-side prediction | `Microsoft.UI.Input.PointerPredictor` (`CreateForInputPointerSource(InputPointerSource)`, `GetPredictedPoints(PointerPoint)`, `PredictionTime`) | yes. Needs an `InputPointerSource` from a `ContentIsland`. **Not tried at runtime.** |
| Device identity | `Microsoft.UI.Input.Interop.PenDeviceInterop.FromPointerPoint()` returns `Windows.Devices.Input.PenDevice` | yes |
| Gesture recognition | `Microsoft.UI.Input.GestureRecognizer` | yes |

What is **not measured** (no pen): whether `Pressure` is the full hardware range or quantised, how many distinct levels a Surface pen produces, how many intermediate points arrive per frame, and whether `TouchConfidence` is enough for palm rejection.

### 3. Headless UWP ink model works inside a WinUI 3 process

`Windows.UI.Input.Inking` data types do not need a window. Runtime probe output (x64 JIT unpackaged, packaged MSIX, and Native AOT all gave the same result):

```
InkStrokeBuilder.CreateStrokeFromInkPoints ok: inputPoints=41 renderingSegments=7 boundingRect=17.149014,21.74113,243.86261,75.52188 width@pressure(first/mid)=0.10/1.00
InkStrokeContainer strokes=1 canPaste=False
Manual Bezier rendering of InkStroke segments via Win2D ok: red pixels=1398 of 42000
```

- `InkStrokeBuilder` + `InkDrawingAttributes.FitToCurve` smoothed 41 input points into 7 cubic Bezier rendering segments, which is the point decimation plus smoothing the spec asks for in §8.3 and the S5 question 5. `InkStrokeRenderingSegment` also carries per-segment pressure, so a variable-width `/AP` can be generated from it.
- Rendering through Win2D needs our own code: `DrawInk` does not exist, so the probe draws the Bezier segments with `CanvasPathBuilder` and a stroke width scaled by pressure.
- `InkAnalyzer`, `InkRecognizerContainer`, `InkManager` also exist in `Windows.winmd` (handwriting recognition, shape analysis). Compile-level only, not run. Their licensing, language packs and future are not assessed.
- Caveat: these are old UWP types projected through the Windows SDK projection. Microsoft's long-term support for them from WinUI 3 is not stated anywhere I found. Treat them as an optional helper, not a foundation.

### 4. Delegated ink (`IDCompositionInkTrailDevice`) from WinUI 3

Raw interop through `dcomp.dll` (`spikes/S5/InkProbe/InkProbe.cs`, `DelegatedInk`). IIDs come from `dcomp.h` in SDK 26100 (`IDCompositionInkTrailDevice` DF0C7CEC-CDEB-4D4A-B91C-721BF22F4E6C, `IDCompositionDelegatedInkTrail` C2448E9B-547D-4057-8CF5-8144EDE1C2DA).

```
DCompositionCreateDevice3(null, IDCompositionDevice) hr=0x00000000
QueryInterface(IDCompositionInkTrailDevice): OK
CreateDelegatedInkTrail hr=0x00000000
IDCompositionDelegatedInkTrail.AddTrailPoints hr=0x00000000 generationId=1
```

- The device and trail objects are creatable on this machine from a WinUI 3 process.
- **The unsolved part is attachment.** WinUI 3's visual tree is `Microsoft.UI.Composition`, which does not expose `IDCompositionVisual`. No WinAppSDK type in 2.5.1 wraps delegated ink (searched). A trail only draws if it is bound into a DirectComposition tree whose target is the window. By the header, `IDCompositionDelegatedInkTrail` is a plain `IUnknown` object (and there is a swap-chain variant, `CreateDelegatedInkTrailForSwapChain`), which suggests it is attached to a visual or tied to a swap chain, but I did not find an official doc page describing the attachment, so this is **unverified**.
- Two candidate designs to test on SURF, neither tried: (i) `CreateDelegatedInkTrailForSwapChain` with the Win2D `CanvasSwapChainPanel` swap chain (needs the raw `IDXGISwapChain` from the panel; its WinUI 3 equivalent of the UWP interop is not checked), (ii) a transparent overlay child window with its own DirectComposition target.
- The classic `[ComImport]` interop used here **fails under Native AOT**: `NotSupportedException 0x80131515: COM Interop requires ComWrapper instance registered for marshalling`. Production code must use source-generated COM (`[GeneratedComInterface]` or CsWin32).

## Surprises

1. **Win2D-WinUI 1.4.0 dropped `DrawInk`.** Any plan that relied on "draw `InkStroke` with Win2D" must render the Bezier segments itself.
2. `Microsoft.UI.Input.PointerPredictor` exists in 2.5.1. It was not in the master prompt or the ADR, and it is the first thing to measure for candidate (b).
3. The old UWP ink *data* model (`InkStrokeBuilder`, `InkStrokeContainer`) works headless, including under Native AOT. Only the *presenter* and controls are missing.
4. The delegated-ink COM objects create fine on a non-pen machine. The blocker is the WinUI 3 composition tree, not the OS.
5. Classic `[ComImport]` does not work under Native AOT. This also affects S5 candidate (c) and S6's shell handler stubs.

## Recommendation (input to ADR-0007)

- Plan on a **custom pipeline (candidate b)**: `PointerRoutedEventArgs.GetIntermediatePoints` into a Win2D surface, with `PointerPredictor` as the first latency lever. Record this as the working assumption until SURF numbers exist.
- Treat **candidate (c)** as a SURF experiment: swap-chain variant first. Do not promise it in the ADR. If neither attachment route works, the fall-back is (b) plus `PointerPredictor` with a revised budget through an ADR (the S5 plan already allows this).
- Use `Windows.UI.Input.Inking.InkStrokeBuilder` only as an optional smoothing helper. Prefer Quire-owned smoothing so the `/Ink` output and the on-screen strokes come from one code path, and so the ink core has no UWP dependency. Decide after measurement.
- Note for the ink surface and S7: a custom-drawn Win2D surface has no UIA peer by default (S6 found this for `CanvasVirtualControl`).

## Go/No-go

- **Provisional / incomplete.** No gate verdict is possible: the latency, pressure and palm tests were not run. The inventory result is **go for a custom pipeline**, **no-go for relying on native WinUI 3 ink**.
- Do not mark S5 as passed. The S5 gate in §17 needs SURF + CAM.
