- Status: **Done on DEV (x64). arm64 is build-verified only, never run. Verdicts are provisional.**

- Author: Sonnet (implementation role). Reviewer: Opus.

- Repo state: branch `m0/spikes`, HEAD `d875702`, **nothing committed**. The spike tree is untracked, so "commit hash" means the base commit plus the working tree.

## Questions

1. Does Win2D 1.4.0 load and draw on Windows App SDK 2.5.1 / .NET 10, on x64 and arm64? (S6 Q1)
2. Does Native AOT publish a WinUI 3 app that runs? Compare ReadyToRun. (Q2)
3. Does single-project MSIX packaging work, with a child engine exe and arm64 native binaries? (Q3)
4. Do the Windows AI APIs (`LanguageModel`, `TextRecognizer`) feature-detect cleanly on a machine that is not a Copilot+ PC? What does `Windows.Media.Ocr` do? (Q4)
5. Do app instancing/redirection, the `.pdf` file type association, and thumbnail/preview handler manifest entries work? (Q5)
6. Does App Content Search exist in 2.5.1 and what happens without a Limited Access Feature (LAF) token? (Q6)
7. Which UI automation driver drives WinUI 3 today? (Q7, feeds ADR-0009)
8. Cold start to the first frame for JIT, R2R and AOT (§11: ≤ 600 ms R1, ≤ 350 ms R3).

### What was built

### Startup measurement (S6.2)

- The harness reads `Stopwatch.GetTimestamp()` (QueryPerformanceCounter) immediately before `Process.Start`, passes it in `QUIRE_T0`, and the app records QPC milestones. QPC is machine-wide, so deltas are valid across processes. The harness cost of `Process.Start` itself is inside the number, which is what a user feels from "launch".
- Milestones: `Main` entry, `Window.Activated`, **first `CompositionTarget.Rendering`** (the headline figure, called "first render" below), and a low-priority dispatcher callback after it ("idle after render").
- "First render" means the XAML framework committed its first frame. I did not capture the DWM present with PresentMon, and the window was not verified as visible at that instant. "Interactive" is approximated by the idle callback. This is weaker than the standard in the spike plan (PresentMon/ETW).
- **Cold is not what the plan defines.** I could not reboot or flush the standby list (no RAMMap, not admin). "First run" below is the first launch of a freshly copied tree (new files, so Defender may scan them), which is a harsher-than-warm number but not a true cold number. **True cold start: not measured.**
- n = 30 warm runs plus 1 first run per mode. The run order was fixed (not randomised) because the machine was shared.
- Packaged modes launch through the execution alias `quires6.exe`.

### 2. Native AOT

Raw outputs: `out/aot-x64-publish.log`, `out/aot-x64-publish-with-vswhere-on-path.log`, `out/aot-arm64-publish.log`.

**First attempt, x64 (as the environment was given):**

```
'vswhere.exe' is not recognized as an internal or external command,
Generating native code
The filename, directory name, or volume label syntax is incorrect.
Microsoft.NETCore.Native.targets(396,5): error MSB3073: The command ""'vswhere.exe' is not recognized ...;
C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Tools\MSVC\14.44.35207\bin\Hostx64\x64\link.exe" @"obj\x64\Release\...\native\link.rsp"" exited with code 123.
```

- The IL compile step **succeeded** ("Generating native code", a 27 MB `HelloQuire.obj`, **zero IL2xxx/IL3xxx warnings**). It failed only at link because the ILCompiler targets call `vswhere.exe` by bare name and `C:\Program Files (x86)\Microsoft Visual Studio\Installer` is not on `PATH`. The error message is misleading: the linker did exist.
- **Second attempt** with that directory added to `PATH` for the process only (nothing installed, nothing changed system-wide): publish **succeeded**. `HelloQuire.exe` is 6.5 MB, the publish folder 87 MB (19 files). It runs, draws (`out/s62-aot-x64.png`), passes the FlaUI test, and its probe output matches the JIT build, except that classic `[ComImport]` COM interop fails: `NotSupportedException 0x80131515: COM Interop requires ComWrapper instance registered for marshalling`. This affects any COM interop code (S5 delegated ink, shell handlers, `dcomp`) and means production code must use source-generated COM.
- **arm64:** `error : Platform linker not found. Ensure you have all the required prerequisites ... For ARM64 development also install C++ ARM64 build tools.` The MSVC 14.44.35207 `lib` folder has `x64`, `x86` and `onecore` only. **Verdict: arm64 AOT blocked: needs the VS C++ ARM64 build tools.** This is a missing component on this machine, not a proven SDK defect. Public reports exist of arm64 cross-arch WinUI AOT failures on .NET 10.0.103 (dotnet/sdk #53387, not reproduced) and an open WinAppSDK issue for single-project MSIX AOT publish on the .NET 11 SDK (#6897, not our SDK).
- Compared with R2R: R2R x64 and arm64 publishes both succeeded with no extra tooling.
- The AOT result is for **this** app. It uses `{x:Bind}`-free XAML with no bindings, no templates and no reflection-based XAML, so it avoids the known AOT pitfalls (binding to non-bindable types, issue reports for WinUI.TableView). A real Quire UI will not be this easy, so "AOT works" is only "the toolchain and the framework work".

### 3. MSIX packaging

- Single-project MSIX with `WindowsPackageType=MSIX` and `EnableMsixTooling=true` works from `dotnet build`. It writes `AppxManifest.xml` and the whole loose layout next to the build output, and adds the `PackageDependency Microsoft.WindowsAppRuntime.2 MinVersion="2.5.1.0"` and the Win2D/WebView2 `activatableClass.inProcessServer` entries itself.
- `Add-AppxPackage -Register <layout>\AppxManifest.xml` worked **with no signing and no certificate** (Developer Mode). `Get-AppxPackage` reports `SignatureKind None`, `IsDevelopmentMode True`. No certificate was created or trusted.
- The packaged exe launches through the `uap3:AppExecutionAlias` and ran every probe. Package identity was visible (`Quire.S6Spike_1.0.0.0_x64__qvwnevk70zn3w`).
- The engine stub inside the package started from the packaged app and reported its architecture. This is a normal child process. An AppContainer child is S3's question and **was not tested here**.
- **Unsigned MSIX sizes** (clean build, `makeappx pack`, includes 7.5 MB `pdfium.dll` and all Windows App SDK managed projections): x64 JIT **17.9 MB**, ARM64 JIT **17.7 MB**, x64 Native AOT **32.8 MB**. AOT is larger because it is self-contained and pulls in `onnxruntime.dll`, `DirectML.dll` and `Microsoft.Windows.AI.MachineLearning.dll` from the `Microsoft.WindowsAppSDK.ML` component. A first pack from an unclean bin folder was 41.5 MB because stale RID folders got in: always pack from a clean layout. The §11 budget is 60 MB per architecture.
- **Surprise:** the MSIX build tooling **forces `MaxVersionTested` to the Windows SDK version of the TFM (26100)** and ignores `AppxOSMaxVersionTestedReplaceManifestVersion=false`, even though the Windows AI docs say it must be ≥ 10.0.26226.0. I patched it with an MSBuild target after build (`PatchMaxVersionTested` in `HelloQuire.csproj`). ADR-0001's `MaxVersionTested="10.0.26300.0"` will not survive the toolchain without a similar step.

### 4. Windows AI feature detection

APIs (verified by compiling against 2.5.1 metadata): `Microsoft.Windows.AI.AIFeatureReadyState`, `Microsoft.Windows.AI.Text.LanguageModel.GetReadyState()`, `Microsoft.Windows.AI.Imaging.TextRecognizer.GetReadyState()`. The namespaces in the brief are right.

Exact observed states. The enum has a **fifth value, `CapabilityMissing`, that the docs table does not list** (docs list Ready, NotReady, DisabledByUser, NotSupportedOnCurrentSystem).

| Case | `LanguageModel` | `TextRecognizer` | Follow-up calls |
|---|---|---|---|
| Unpackaged (JIT and AOT) | `CapabilityMissing` | `CapabilityMissing` | `CreateAsync()` throws `UnauthorizedAccessException 0x80070005 "Denied access"` for both |
| Packaged **without** `systemai:Capability systemAIModels` | `CapabilityMissing` | `CapabilityMissing` | `LanguageModel.CreateAsync` throws `COMException 0x80004005 "Not declared by app"` |
| Packaged **with** `systemAIModels` and MaxVersionTested 26300 (JIT and AOT) | **`NotSupportedOnCurrentSystem`** | **`NotSupportedOnCurrentSystem`** | `LanguageModel.CreateAsync` throws `COMException 0x80070490 "Element not found ... Package Quire.S6Spike_... not found"`; `TextRecognizer.CreateAsync` throws `COMException 0x80070490 "Element not found."` |
| `LimitedAccessFeatures.TryUnlockFeature("com.microsoft.windows.ai.languagemodel", "", ...)` with no token | `Unavailable` | n/a | state unchanged afterwards |

- On DEV (Intel AI Boost NPU, RTX 5080, Developer Mode on) both features report **`NotSupportedOnCurrentSystem`**: the clean "hide the feature" answer. The Intel NPU does not qualify. No exception came from `GetReadyState` itself in any case.
- `EnsureReadyAsync` was **not called** (it could start a model download, which nobody authorised). The two `CreateAsync` calls were made only because the state was not `NotReady`; they throw instead of downloading, so the lesson for ADR code is: **gate on `GetReadyState()` and never call `CreateAsync` unless `Ready`**. The exception text for the unsupported case is unhelpful ("Package ... not found", "Element not found").
- The feature id strings (`com.microsoft.windows.ai.languagemodel`, `com.microsoft.windows.ai.appcontentindexer`) are not in the public docs I read. I found them as strings in the framework DLLs shipped in the NuGet packages (`Microsoft.Windows.AI.Text.dll`, `Microsoft.Windows.Search.dll`). That is evidence of what the runtime asks for, not a documented contract.
- **OS minimum for Windows AI on retail Windows (ADR-0001 UNVERIFIED row):** the get-started page, last updated 2026-10-14, still says "Install Windows 11 Insider Preview build 26120.3073 ... or later" and `MaxVersionTested` ≥ 10.0.26226.0. It names no retail build. Still unresolved. R2 (a real Copilot+ PC) is required to see `Ready`/`NotReady`.
- **`Windows.Media.Ocr`** works on DEV, packaged, unpackaged and AOT: `AvailableRecognizerLanguages` = `en-GB, en-US`; OCR of the PDFium-rendered sample page at 2x returned all four lines exactly, with the words and numbers intact: "Quire spike S6 OCR test The quick brown fox jumps over the lazy dog. Windows App SDK 2.5.1 with Win2D 1.4.0 PDFium chromium 8125 - page 1 of 1 - 0123456789" in **22 to 35 ms** (one image, warm). This is a single clean synthetic page. It says nothing about accuracy on scans.

### 5. App Content Search

- `Microsoft.Windows.Search.AppContentIndex` types **exist in 2.5.1** (`Microsoft.WindowsAppSDK.Search` 2.5.5): `AppContentIndexer`, `GetOrCreateIndexResult`, `AppIndexTextQuery`, `AppManagedIndexableAppContent`, `IndexCapabilities` and more. Static methods found by reflection: `GetOrCreateIndex`, `GetIndexCapabilitiesOfCurrentSystem`, `DeleteIndex`, `GetExistingIndexes`.
- Without a LAF token: `TryUnlockFeature("com.microsoft.windows.ai.appcontentindexer", "", ...)` returned `Unavailable`, and `AppContentIndexer.GetOrCreateIndex("s6probe")` threw **`UnauthorizedAccessException 0x80070005: "Limited Access Feature is not available: com.microsoft.windows.ai.appcontentindexer. Status: 0"`**, unpackaged and packaged alike. The exception is clean and catchable. (The docs also require package identity and the `systemAIModels` capability.)
- No token was requested or used. I did **not** test whether the API works on a non-Copilot+ device with a token. Capability probing (`GetIndexCapabilitiesOfCurrentSystem`) was not called: it was not clear whether it needs the token.

### 7. UI driver smoke test (S6.6)

- Findings from the UIA tree dump: `AutomationId` set on XAML elements (`AutomationProperties.AutomationId`) is exposed. The window class is `WinUIDesktopWin32WindowClass`. - **Appium (desk research only, nothing installed):**
  - `appium-windows-driver` (6.3.1 on npm) **is a proxy to Microsoft's WinAppDriver** and needs it installed separately since driver 3.0.0 (`install-wad` script or manual download). It needs Developer Mode and `appium:app` or `appTopLevelWindow`. Its README lists support for UWP, WinForms, WPF and Win32 and **does not mention WinUI 3**.

An open Appium PR (#22917) would rename the `windows` shortcut to `wincore`.
  - Neither WinCore nor NovaWindows lists WinUI 3 explicitly in the sources I read. Both are untested by me.
  - Sources: [appium-windows-driver README](https://github.com/appium/appium-windows-driver), [appium-wincore-driver](https://github.com/appium/appium-wincore-driver), [Appium PR 22917](https://github.com/appium/appium/pull/22917).

### 8. Startup numbers (S6.2)

All numbers are milliseconds from the QPC timestamp taken just before `Process.Start` to the first `CompositionTarget.Rendering` ("first render"). Unpackaged rows run from a fresh copy of the publish folder. Packaged rows launch through the alias. x64 only (arm64 cannot run here). Release builds, framework-dependent JIT and R2R, self-contained AOT. Base commit `d875702` plus untracked spike tree. The PDFium page render runs in the Win2D `CreateResources` handler during startup, so it is **inside** these numbers, though the first-render timestamp can fire before it finishes (not checked).

**Load warning: system CPU was 100% before every batch and averaged 100% during every run, because other agents were building on this machine.** The harness logged it per run. These are therefore worst-case-ish numbers on a shared box, **not** clean DEV numbers, and DEV is neither R1 nor R3. A tiny smoke test before the real run (n = 3 JIT warm, system CPU 24 to 33%) gave first render 319 to 334 ms, which shows how much the load inflates the figures below. That smoke test was not recorded as a result (n = 3, different load).

What the data supports, and what it does not:

- **Native AOT is the fastest and the most stable under load**: warm first render p50 428 to 431 ms, p95 493 to 566 ms in two independent rounds. R2R p50 531 to 565 ms. JIT p50 526 to 670 ms with a p95 up to 970 ms. JIT's two rounds differ by 140 ms at the median, so only the ordering AOT < R2R ≲ JIT is stable. The R2R vs JIT gap is within the round-to-round noise.
- AOT cuts `Main()` entry from about 230 to 315 ms (JIT) to about 185 ms. Runtime startup, not XAML, is a large part of the fixed cost.
- **Packaged launch is slower**: warm p50 JIT 879 ms and AOT 607 ms through the alias, against 670 and 428 unpackaged in the same round. The alias launch adds work (package activation, `Main()` p50 336 to 516 ms against 184 to 315). Packaged p95s of 1.2 to 1.4 s show contention. Packaged startup is what ships, so this needs a re-measure on an idle machine. Only round 1 exists for packaged modes.
- **§11 budgets (600 ms R1, 350 ms R3): no verdict.** Best warm p50 here is 428 ms (AOT) on a saturated 24-core machine. The fastest single warm run in any round was 355 ms (AOT). Nothing here shows the budget is met or missed on R1/R3. A clean re-run on an idle machine, with ETW or PresentMon, is required.
- Not measured: true cold start (reboot or standby flush), R1, R3, R2, arm64 of any mode, ETW or PresentMon first-present time, memory.


### 9. Ink API inventory

See [S5.md](S5.md) (partial). Short version: no `InkCanvas` or ink presenter in WinUI 3 / 2.5.1; pressure, tilt, barrel, eraser, intermediate points and `PointerPredictor` all exist; Win2D 1.4.0 has no `DrawInk`; delegated ink COM objects create but cannot be attached to the WinUI 3 tree from what I found.

## Surprises

1. **Win2D 1.4.0 (built for WinAppSDK 1.8) works on 2.5.1** with no warnings, unpackaged and packaged, JIT and AOT.
2. **Native AOT works end to end on x64**, with no IL warnings, but the "link.exe not found" error is a PATH problem (`vswhere.exe`). The machine **did** have an MSVC toolchain, in VS Build Tools 2022, that the task said it did not.
3. **`dotnet build` alone builds a WinUI 3 app and an MSIX layout.** No Visual Studio WinUI workload was needed (XamlCompiler ships in the NuGet package). VS 2026 Community with only the managed desktop workload was enough.
4. The MSIX tooling **overwrites `MaxVersionTested`** with the TFM's SDK version, which breaks the Windows AI docs' requirement unless patched.
5. `AIFeatureReadyState` has an undocumented fifth value `CapabilityMissing`, and the "not supported" `CreateAsync` exceptions carry misleading text.
6. The COM surrogate server entry **must be at Application level** for the thumbnail/preview `Clsid` key reference to resolve. Package-level fails schema validation.
7. A **`CanvasVirtualControl` is invisible to UI Automation**. Anything custom-drawn needs its own peer (S7).
8. **Classic `[ComImport]` fails under Native AOT** with a COM interop error. Source-generated COM is mandatory for the shell handlers and the engine IPC wrappers if they use COM.
9. AOT packages are bigger (32.8 MB vs 17.9 MB) because the AOT publish carries the ML runtime (`onnxruntime.dll`, `DirectML.dll`). `Microsoft.WindowsAppSDK` is a meta-package that pulls Foundation, WinUI, AI, ML, Search, Widgets, DWrite. Referencing only what Quire needs would shrink it. Not tried.
10. A single `Add-AppxPackage -Register` is enough in Developer Mode: no cert, no trust-store change, as the brief hoped.
11. The WinAppSDK 2.x framework package lets an unpackaged JIT/R2R app run only because the 2.5.1 framework package is installed on this machine. A user without it would need the runtime installer. Not tested on a clean machine.

## Recommendation

### Input to ADR-0001 amendments

- **Win2D row (D2):** change UNVERIFIED to "VERIFIED on x64 on DEV: works on 2.5.1 with .NET 10 (packaged and unpackaged, JIT and AOT). arm64 runtime unverified: needs R2."
- **Deployment mode row:** "Native AOT builds and runs on x64 with MSVC 14.44 `link.exe` and `vswhere.exe` on PATH. arm64 AOT is blocked here: needs the VS C++ ARM64 build tools. Keep AOT as the target but **do not drop R2R**: R2R builds on both architectures with no extra tooling. Decide the default after startup measurements on R1/R2/R3."
- **.NET row:** record that DEV used SDK 10.0.300 / runtime 10.0.8 against the pin 10.0.403 / 10.0.14, and add `global.json` handling.
- **Windows AI row:** record `NotSupportedOnCurrentSystem` on a non-Copilot+ DEV box, `CapabilityMissing` without the manifest capability, the `systemAIModels` requirement, and the `MaxVersionTested` workaround. The retail OS minimum is still unverified.
- **App Content Search row:** add "LAF denial surfaces as `UnauthorizedAccessException 0x80070005` with the text `Limited Access Feature is not available: com.microsoft.windows.ai.appcontentindexer`".
- **Packaging:** `MaxVersionTested` needs a post-build patch; unsigned loose registration works in Developer Mode; plan the AOT+MSIX manifest step.
- **UI automation row:** FlaUI works against WinUI 3 today. The Appium Windows driver is deprecated and proxies the unmaintained WinAppDriver.
- Add a new row: **use source-generated COM** (not `[ComImport]`) for anything that must work under AOT.

### Input to ADR-0006 (rendering surface)

- **Choose Win2D `CanvasVirtualControl` as the primary surface.** It works on 2.5.1. Keep Composition as the documented fallback only if arm64 or throughput (S2) fails.
- The surface needs a **custom UIA peer** regardless (Win2D gives none). That is S7's question.
- S2 should use the same pdfium-to-`CanvasBitmap.CreateFromBytes` path as a baseline: it works, but I did **not** measure its cost.

### Input to ADR-0009 (UI test driver)

- **FlaUI.UIA3 5.0.0 is the working choice today** (smoke test passes for JIT, AOT and packaged). It is a library, not a driver server, so it needs no extra install. Last release 2025-02-25, so maintenance risk remains.
- Do not select Appium Windows driver/WinAppDriver. If an Appium-style driver is wanted, evaluate **appium-wincore-driver** and **NovaWindows** on a real WinUI 3 app first. Neither lists WinUI 3 and I tested neither.

### Other

- For packaged startup, measure through the alias, not the unpackaged exe: the packaged path is what ships.
- ADR for single-instance routing: the redirect pattern in `Program.cs` works as is, including delivering `File` activations to the key instance.

## Go/No-go

**Provisional GO on x64 for the Win2D + WinUI 3 + MSIX stack.** Reasons: Win2D draws on 2.5.1, MSIX works unsigned in Developer Mode, instancing and FTA work, FlaUI works. **Provisional because:**

- arm64 was only build-verified, never run. The S6 pass criterion needs both architectures. **Not passed.**
- Native AOT on arm64 is **blocked: needs VS C++ ARM64 build tools**.
- The startup budget verdict needs R1 and R3, not this loaded DEV machine. **Not passed, not failed.** See section 8 for the numbers and their caveats.
- Windows AI was only checked on a non-Copilot+ machine. `Ready` was never seen.
- The "cold" requirement (reboot or standby flush) was not met.

Per §19.3 I mark no gate as passed.
