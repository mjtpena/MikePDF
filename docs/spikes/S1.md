### 2.3 How the API checker decides things

- A **function** is any `FPDF_EXPORT` declaration (so the four `#define FPDF_EXPORT` lines are excluded). The name is the identifier after `FPDF_CALLCONV`.
- A function is **Experimental** if the contiguous `//` comment block directly above it contains `Experimental API`. Blank lines inside a block do not break it. This was needed for `FPDFDoc_CloseJavaScriptAction`, whose block has a stray blank line.
- Cross-check: the number of functions flagged Experimental equals the number of `// Experimental API` markers in every one of the 22 headers (238 = 238). If a header had a marker that did not attach to a declaration, the two numbers would differ.
- Each function also records the `#if` conditions it sits under, limited to `PDF_ENABLE_XFA`, `PDF_ENABLE_V8`, `PDF_USE_SKIA`, `_WIN32`, `WIN32`.
- "Exported" means the name appears in the PE export table. Ordinal-only exports: none in any DLL.

### 2.4 Smoke test design

`spikes/S1/smoke/Program.cs` loads each fixture through `FPDF_LoadCustomDocument` with a `FPDF_FILEACCESS` callback over a managed `byte[]`, so no path is ever given to PDFium. For each fixture it then:
1. reads the page count and page 0 size (`FPDF_GetPageSizeByIndexF`);
2. renders page 0 into a caller-owned BGRA buffer (`FPDFBitmap_CreateEx`, white fill, `FPDF_RenderPageBitmap` with `FPDF_ANNOT`), counts non-white pixels, and renders again with `FPDF_RenderPageBitmapWithMatrix`;
3. loads the text page, reads the char count, the first characters, and the first character's box;
4. walks top-level bookmarks, reads `Producer` through `FPDF_GetMetaText`, and counts signatures (reading the SubFilter of each);
5. saves to memory through a `FPDF_FILEWRITE` callback with `FPDF_NO_INCREMENTAL` and with `FPDF_INCREMENTAL`, then reopens the output and compares the page count.

It also feeds 17 bytes of garbage and expects a null handle plus a typed error from `FPDF_GetLastError`. It uses library config version 2 (AGG renderer, default fonts), does not touch the Fontations or Brotli fields, and ends with `FPDF_DestroyLibrary`. The process is x64, so only the x64 and v8-x64 DLLs could be run. **The arm64 DLL was not executed: this machine cannot run arm64 binaries.** For arm64, only static PE analysis exists.

`args.gn` files shipped with the prebuilt (identical key set apart from the V8 extras):

|---|---|---|---|

| `pdf_is_standalone` | true | true | same |
| `pdf_use_partition_alloc` | false | false | same |

| `v8_use_external_startup_data` | not set | false | n/a |
| `v8_enable_i18n_support` | not set | false | n/a |
| `treat_warnings_as_errors` | false | false | same for PDFium. Our own code is stricter |
| `target_cpu`, `target_os` | `x64` or `arm64`, `win` | `x64`, `win` | same |
| `VERSION` | 158.0.8125.0 | 158.0.8125.0 | `build/pdfium.lock` pins a Chromium stable branch (D3), not this trunk snapshot |

Differences that matter:
1. **V8 and XFA are tied together in the prebuilt.** Its configure step sets `pdf_enable_xfa` to the same value as `pdf_enable_v8`. There is no XFA-without-V8 build and no V8-without-XFA build in the prebuilt, so the plan's configs (b) "V8 on" and (c) "XFA on" are the **same binary** there. In PDFium's own GN they may be separable. I wrote `args/v8.gn` (V8, no XFA) and `args/xfa.gn` as distinct configs, but whether the first one generates is **not verified**.
2. **No hardening beyond defaults.** The prebuilt sets none of the §13.2 flags explicitly. What it has is in 3.2. `/Qspectre`, `/sdl`, `/guard:ehcont` and XFG are not requested (and not visible, or absent, in the binary).
3. **Static linking of the runtime and a source patch.** Upstream declares `component("pdfium")`, so `is_component_build = false` produces a static library, and the upstream `fpdfview.h` defines `FPDF_EXPORT` as empty outside component builds. pdfium-binaries patches `BUILD.gn` to `shared_library("pdfium")` and rewrites that section of `fpdfview.h` so `FPDF_EXPORT` is always `__declspec(dllexport)` when building and `dllimport` when consuming. The shipped package still contains the original as `include/fpdfview.h.orig`. **We would need the same patch** (or our own) for any own build. That patch set is under pdfium-binaries' licence (the ADR records "MIT" in the repo and "Apache-2.0" on NuGet, which differ).
4. **AGG renderer only.** `FPDF_RenderPageSkia` is not exported. The font backend in the prebuilt is not stated anywhere I read. The header's `FPDF_LIBRARY_CONFIG` (version up to 7) has a font-backend field (FreeType or Fontations) and a Brotli flag, and the header warns that selecting something the build lacks "will fail with an immediate crash". The smoke test leaves those fields untouched.
5. **No symbols, unsigned.** No PDB ships with the prebuilt and the DLL has no Authenticode signature. Crash-dump symbolication (§14) and a code-integrity policy in the sandbox (S3) both need our own build or our own signing.
6. **The prebuilt is a trunk snapshot** (ADR-0001 D3), not a Chromium stable branch.

A converted screenshot of the `hello_world.pdf` render shows both lines in a sans-serif and a serif face. The system font path therefore worked in this unsandboxed process.
- `FPDF_RenderPageBitmapWithMatrix` (returns `void`, which the first version of my P/Invoke got wrong) gave nearly the same non-white counts as the plain render (for example 1,934 vs 1,939 on `hello_world.pdf`). The differences were not examined.
- `bookmarks.pdf` lists its three top-level bookmarks. `annotation_highlight_long_content.pdf` has `Producer = "Skia/PDF m54"`.
- Every saved output reopened with the same page count, for both save modes.
- Garbage input returned a null handle and `FPDF_GetLastError() = 3` (`FPDF_ERR_FORMAT`), not a crash.
- **Timings are not reported as results.** Three runs of the same binary gave `FPDF_InitLibraryWithConfig` between 3.4 and 21.2 ms and the first document load between 0.7 and 100 ms. These are single cold-process Stopwatch samples with JIT and background load, so they carry no information. The V8 DLL's init time (18.0 ms in one run) is **not** comparable to the no-V8 one for the same reason. **Not measured.**
- Not exercised: forms (`FPDFDOC_InitFormFillEnvironment`, `FORM_*`), annotation creation, progressive rendering, link and destination APIs, structure tree, attachments, import/flatten. They are proven present and exported, not proven working.

## 4. Surprises

1. **Half the API is Experimental.** 238 of 478 functions (49.8%). Nothing in annotations, signatures or attachments is stable, and `FPDF_GetPageSizeByIndexF`, the function a viewer calls first, is Experimental while its stable twin is marked as "will be deprecated". Every pin bump needs an automated API-diff, as ADR-0001 already says. `out/functions.csv` is a ready baseline for that diff.
2. **The prebuilt only works because of a header and build patch.** Without it, a non-component build exports nothing. Any own build must carry the same patch, which makes the "own build" a patched-upstream build, not a vanilla one.
3. **The engine is not free of Win32k.** It imports 47 `gdi32` and 3 `user32` functions, mainly for fonts (`CreateFontIndirectA`, `EnumFontFamiliesExA`, `GetFontData`). That bears directly on S3's questions about Win32k lockdown and the font path inside an AppContainer. The imports are static (no delay-load), so an engine process that cannot load `gdi32` or `user32` would fail at load time, not at first use. I have not tested that.
4. **`FPDFAnnot_GetFormFieldType` lives in the Experimental annotation header**, so the forms area depends on Experimental API even though every `FORM_*` function in the checklist is stable.
5. **XFA cannot be had without V8** (prebuilt), and the V8 build leaks a non-PDFium export (`CrashForExceptionInNonABICompliantCodeRange`).
6. **The header knows about build options the prebuilt may not have.** Config v5 to v7 add a Fontations font backend, a Brotli filter flag, and per-document isolates. A request for one that the build lacks is documented to crash at init.
7. **Incremental save of an unmodified document is not a no-op.** `hello_world.pdf` grew from 840 to 1,638 bytes and `annotation_highlight_long_content.pdf` from 38,455 to 58,978 bytes, while the full save was smaller than the source in 5 of 6 cases. I did not investigate why. S4 should look at what PDFium appends.
8. **The fixture folder holds 298 PDFs, not the 343 the brief said.** There are 2,237 files in total. I did not look for the difference.
9. **The machine's .NET is older than the ADR pin** (SDK 10.0.300 and runtime 10.0.8 vs 10.0.403 and 10.0.14).

---

## 5. Recommendation

This is **input to ADR-0002**, and provisional while the from-source half is blocked.

1. **Which build ships:** a **no-V8, no-XFA, AGG, shared-library `pdfium.dll` built from source by us**, per architecture (x64 and arm64), from a **Chromium stable branch**. JavaScript (V8) and XFA stay out of the default build. Reasons from this spike:
   - The prebuilt is unsigned, ships no PDB, is a trunk snapshot, and sets none of our hardening flags explicitly.
   - The prebuilt's size already fits the budget at about half of it, so there is room for a few hardening costs.
   - V8 adds 23.6 MiB raw / 8.5 MiB deflated (x64) and a second attack surface, for a feature (JS in forms) that §13.3 already puts behind a security gate.
2. **Until the own build exists, M1 and the other spikes keep the pinned prebuilt.** It is hash-pinned and its API surface and hardening are now characterised, but it must not be the release build.
3. **V8/XFA:** keep as a separate, optional flavour decided later. If it is built, treat "V8 on" and "XFA on" as one switch (they are one switch in the prebuilt).
4. **Link mode:** shared library, one `pdfium.dll` with no companion DLLs. The prebuilt shows it works and imports only four system DLLs. Static linking would need the engine process to link PDFium and would change how symbols are exported, and nothing here favours it.
5. **Wrapper policy for Experimental API:** wrap all 238 in `Quire.Engine` behind one thin layer, add an export-and-signature diff to the weekly PDFium job, and prefer a stable function where the headers offer one (3.3).
6. **Hardening:** keep the three prebuilt-observed flags, and add an automated read-back (`symdiff.py`) to CI so a toolchain default change cannot silently remove them. Decide separately whether `/guard:ehcont`, XFG and `/Qspectre` are worth requesting.
7. **Fuzzing (S1.5, planned, not done):** build our own PDFium with clang-cl and `is_asan = true`, `use_libfuzzer = true` (arg names unverified on Windows), link `spikes/S1/fuzz/fuzz_target.cc` (open from memory, render page 0 at 256x256) with `-fsanitize=fuzzer,address`, seed the corpus from `spikes/_shared/corpus/pdfium-resources/`, and run it under the same clang-cl runtime libraries that Chromium's toolchain ships. If the arg names do not hold on the pinned branch, PDFium's own `testing/fuzzers` GN targets are the fallback. I could not test any of this.

---

## 6. Go / No-go

**Provisional GO**, on these grounds only:
- **Established (measured):** the API surface is complete. All 65 checklist functions are present, and exported on x64 and arm64. The prebuilt works end to end on x64 (load through custom file access, render, text, bookmarks, signatures, save in memory, typed error on garbage). The size budget has room (≤ 15 MB vs 7.59 / 6.90 MB for the prebuilt).
- **Not established (blocked):** that we can build x64 and arm64 from source, that the hardening flags survive our own build, that arm64 needs no emulation, the V8/XFA build cost, and ASan/libFuzzer. The plan's pass criterion on "builds natively for both architectures" is therefore **unmet, not failed**.
- **Standing risk, not a blocker:** half the API is Experimental (Surprise 1).

The gate in §17 should not treat S1 as complete until the from-source steps run on a machine with the toolchain in 3.5.

## 7. Open questions for Opus

1. **Who or what builds from source?** This machine needs admin to install the VS C++ workload and SDK. Options: elevate here; use another dev box; use a larger CI runner (R-19 says the private-repo hosted runner is too small for a per-PR build, but a one-off spike build may still be feasible). Which one?
2. **JavaScript in v1?** If no, ADR-0002 can drop V8/XFA from the shipping matrix and S1's V8/XFA measurements stay informational.
3. **Which PDFium branch is the release pin?** ADR-0001 proposes `chromium/8103` (M157). `fetch.ps1` defaults to the prebuilt's `chromium/8125` so that results compare. Do I switch it for the real run?
4. **Patch provenance.** Do we vendor the pdfium-binaries patches (shared library, header export, `clang_rt`, `win/build.patch`, `resources.rc`) into the repo, pinned by commit, or write our own? `build.ps1` downloads them from `master` and says so.
5. **ARM64 hardening.** What do we require instead of `/CETCOMPAT` on arm64 (PAC, BTI, nothing)? I did not check the arm64 binary for either, and I have not verified that CET is x64-only.
6. **Are `/Qspectre`, `/sdl`, `/guard:ehcont` and XFG requirements or nice-to-haves?** They cannot be read from the PE headers (the first two) or are absent (the last two).
7. **Engine imports `gdi32` and `user32` statically.** Should S3 treat Win32k lockdown as out of scope for the engine process, or is a PDFium patch (or a custom font provider via `FPDF_SYSFONTINFO` plus a GDI-free path) wanted? This changes what S1 should ask of a source build.
8. **Is the 15 MB per-architecture budget meant for the DLL alone or for the MSIX share?** The 60 MB total is tight only if V8 ships.
9. **Fixture count:** 298 `.pdf` found vs 343 stated. Is something missing from the corpus fetch?
10. **Symbols:** where do our own PDBs go (§14: "published privately")? The prebuilt gives none.
