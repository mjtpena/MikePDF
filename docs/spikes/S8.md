## 1. Questions

From the S8 section of the spike plan, plus the pass/fail rule:

1. Does the PDFium signature API give enough to validate (byte range, contents, subfilter, time, DocMDP), or do we need our own parsing in `Quire.PdfWriter`?
2. Can .NET `SignedCms` verify `adbe.pkcs7.detached` and `ETSI.CAdES.detached`, and does `X509Chain` give trust status, including offline revocation behaviour?
3. Can we write an incremental update (signature field + widget + `/V` + `/Contents` and `/ByteRange` placeholders), patch both in place after signing, and leave the xref intact?
4. Can CNG keys sign through `CmsSigner` (test cert; smart card / Windows Hello if available)?
5. Can we detect changes made after signing (revision comparison) on known attack fixtures?
6. Pass/fail: every fixture classified correctly; output cryptographically valid in Acrobat Reader; **any false "Valid" on a tampered or attack fixture fails the spike.**

### 2.4 Fixtures and where the attack designs come from

All 42 fixtures are generated by spike code (`fixtures/Generator.cs`); none were downloaded, so there is no third-party redistribution question. Each manifest entry carries a `Licence` field ("generated by spike S8 code; no third-party content"). The four signature PDFs in the PDFium corpus are BSD-3-Clause and are not copied.

**Honesty note on the research source.** The task asked for the attack designs to be based on the published "PDF Insecurity" research (Ruhr University Bochum, 2019 to 2021). The spike also forbids network access, so **I did not fetch or re-read the papers or the project site this session.** The designs come from my background knowledge of the three 2019 classes (universal signature forgery, incremental saving attack, signature wrapping) and the 2021 shadow attacks (hide, replace, hide-and-replace). Fixture realism against the original samples is therefore **not verified**. Opus should have someone compare them with the papers before ADR-0012 leans on this table.

| Needed for validation | PDFium API |
|---|---|
| Offset and extent of the `/Contents` token (to prove the `/ByteRange` gap is exactly that token) | not available. **Partial workaround found:** `/Contents` is returned zero-padded to the placeholder size, so a normal file satisfies `(b2 - b1) == 2 * contentsLen + 2`; the gap-smuggling fixture returns `contentsLen = 2003` against a 32770-byte gap. | CMS structure (certs, signer, algorithms, attributes) | raw bytes only; all parsing is ours (`SignedCms`) |

| Stability | whole header is "Experimental API" and read-only |

**Answer to Q1: PDFium enumeration is enough to list signatures and read their metadata (and to cross-check ours), and nothing more.** Validation, modification analysis and signing need our own PDF object/revision layer. Nothing in the pinned headers makes `Quire.PdfWriter` optional here.

#### 3.2.2 Findings against my own validator (reported in full, nothing was hidden)

1. **A false "Valid" was produced during development and fixed.** The first version of `sneaky-duplicate-keys` (a later revision redefines the page with `/Contents` twice: the evil stream first, the signed stream last) was reported **Valid**. My parser keeps the last duplicate, so it saw "no change", while a first-wins reader would show the new stream. Fix: the parser records duplicate keys and the analyzer treats a duplicate introduced after signing as Disallowed. Re-run: Invalid. pyHanko's strict reader rejects the file outright. This class (parser differentials) is the main way a hand-written revision comparer can lie.
2. **First full run scored 17/31 for the wrong reason**: a bug in my xref reader (`SkipWs` also skips `%%EOF` as a comment) made every real signature fail the "revision ends at %%EOF" check. Only after fixing it did the scores mean anything. Tamper fixtures were "correctly" Invalid in that run for the wrong reason; the table in this report is from runs after the fix.
3. **`sigdict-duplicate-keys` was a false alarm of mine.** My first run showed Valid because my own test hook silently failed to apply (the file had no duplicate). After fixing the hook it is Invalid. Not a validator miss.
4. **Validator changes made after seeing results:** (a) duplicate-key detection (finding 1); (b) a newly added **empty but visible** signature field is a warning, not silently allowed (the overlay vector); (c) a signature dictionary not reachable from the final `/AcroForm` is capped at Unknown even if cryptographically intact; (d) `RevocationStatusUnknown` / `OfflineRevocation` alone no longer fails the chain; (e) XMP `/Metadata` replacement became Allowed (pyHanko and Acrobat rewrite it on every signing); (f) cycle-assumed "equal" results are not cached; (g) the AcroForm walk failing now falls back to carving instead of dropping signatures.

#### 3.2.3 What the validator does not catch (known residual risk)

- **Permitted-change overlays.** Annotations (P=3 or no DocMDP), form-field fills and new signature fields are permitted changes by definition and can visually cover content. Quire reports `ValidWithWarnings` with the change list (`shadow-annot-overlay`, `sigfield-overlay`, `annot-after-sign-*`). It does **not** compare renderings. A visual diff of the signed revision against the final one (PDFium can open the prefix `[0, ByteRange end)` as its own document) is a plausible complement; **not tried**.
- XFA, FieldMDP / `/Lock`, `/DocMDP` on non-first signatures, document timestamps (`ETSI.RFC3161`: enumerated, not validated), RSA-PSS, SHA-3, encrypted files with object streams (analysis refuses), and signatures whose `/Contents` is inside an object stream (illegal per spec).
- Revocation by OCSP: **not measured** (no responder built).

### 3.5 Chains, trust and revocation (Q2) and CNG (Q4)

`SignedCms` verified both subfilters (adbe.pkcs7.detached and ETSI.CAdES.detached), RSA-3072 and ECDSA P-256, with the PDF bytes supplied as detached content. `/Contents` must be cut to the ASN.1 length first (`AsnReader.PeekEncodedValue`); the zero padding makes `SignedCms.Decode` unusable on the raw token. An attached payload inside a "detached" signature is not rejected by `SignedCms`; the validator has to check it (`usf-attached-content`).

`X509Chain` + `CustomRootTrust` worked for RSA and ECDSA roots. Measured behaviour (loopback CRL server, in-memory CA; see `out/fixtures/revocation.json`):

| Scenario | Mode | Flags | CRL fetched |
|---|---|---|---|
| Leaf without CDP/OCSP | NoCheck | NoError | no |
| Leaf without CDP/OCSP | Offline / Online | **RevocationStatusUnknown** (`Build` returns false) | no |
| CDP set, server down, no cache | Offline | RevocationStatusUnknown, OfflineRevocation | no |
| CDP set, server down, no cache | Online | same, **after about 2.1 s** (timeout set to 5 s) | no |
| CDP set, server up, not revoked | Online | NoError | yes (1) |
| same, second call | Online | NoError | no (served from the OS cache) |
| same, Offline with warm cache | Offline | NoError | no |
| `DisableCertificateDownloads = true`, CDP set | Online | NoError | **yes (1)** |
| CDP set, leaf revoked | Online | **Revoked** | yes |

Consequences: (1) `DisableCertificateDownloads` stops AIA certificate downloads, **not CRL fetches**; the only way to keep the validator off the network is `RevocationMode.NoCheck`, which is what the spike used. (2) Online revocation contacts the CA's CDP, a privacy leak that the product must make an explicit, opt-in policy. (3) A missing or unreachable revocation source comes back as a status flag, not an exception, so the product needs an explicit mapping (the spike maps it to a warning). **OCSP: not measured.**

**Windows-store trust (Q2): not demonstrated.** Against the system store a self-signed test root correctly comes back untrusted (`untrusted-root`: Unknown). Chaining to a real CA root was attempted with the Authenticode signer of the local `dotnet.exe`; the result was `PartialChain` because the intermediate certificate was not available offline. A real CA-signed PDF, and AATL/EUTL list import, remain a **manual follow-up**.

**CNG (Q4):** `RSACng` and `ECDsaCng` keys created **non-exportable and ephemeral** sign through `CmsSigner` (`new CmsSigner(IssuerAndSerialNumber, cert, key)`; RSA-3072 15 to 39 ms for the CMS across runs on first use, ECDSA about 1.5 ms) and the output validates Valid. Two caveats: `CertificateRequest.CreateSelfSigned` throws `The requested operation is not supported` for a non-exportable CNG key (it needs to export to attach the key), so the cert had to be issued with an `X509SignatureGenerator` and the key passed separately; and `CmsSigner` was called with `silent: true`. **Not measured:** keys persisted in a key store, certificates from the Windows store, smart cards (PIN flow), Windows Hello keys, and what `silent: true` does for a PIN-protected key. Those need a physical or VM pass.

## 4. Surprises

1. **A parser differential produced a false Valid in my own first validator** (duplicate dictionary keys, 3.2.2). Any revision comparer needs a differential policy for duplicates from day one.
2. **pyHanko accepts an empty visible signature field with an opaque appearance** over the page as "acceptable form filling" (`sigfield-overlay`). Quire warns; the permitted-changes model means every such overlay vector must be surfaced to the user.
3. **pyHanko 0.38.0 rejected all three annotation-after-signing fixtures**, including the DocMDP P=3 one where the spec allows annotations. Reader behaviour on annotations is a product policy decision, not a fact.
4. **`DisableCertificateDownloads` does not stop CRL requests.**
5. **PDFium counts empty signature fields** as signatures, returns `/Contents` zero-padded, and cannot express byte ranges above 2 GiB.
6. **`docmdp.pdf` has no `/ByteRange`**, so a byte-range grep undercounts signed corpus files.
7. **`CmsSigner` adds no signingTime by default**, which already matches PAdES B-B (ETSI says to rely on `/M`); the pkcs7 variant needs it added explicitly.
8. The strict parser rejects sloppy-but-viewable PDFs (a missing `endobj`) that PDFium opens. Strictness cannot cause a false Valid, but it causes false Unknown / Invalid on real-world files. Tooling note: shell heredocs in this environment altered backslash escapes several times, which caused compile errors and one silently failed scripted edit (3.2.2 item 3); later edits used the editor tool.

## 5. Recommendation

**P1 signing and validation are feasible with .NET `SignedCms`/`CmsSigner`, PDFium for enumeration/rendering and our own revision layer.** For ADR-0012 and `Quire.PdfWriter`:

1. **Own the PDF revision layer in `Quire.PdfWriter`.** PDFium cannot supply byte-range token offsets, revision views or object diffs. The spike's `core/` + `validate/ModificationAnalyzer.cs` + `sign/` are the working prototype of that layer (parser incl. xref streams / object streams / hybrid, serializer, incremental writer, revision views). Keep the analyzer's rule "unknown difference is Disallowed".
2. **Validator contract (suggested for the ADR):** report three axes (Integrity, Identity, Modifications) and derive the four statuses; reject on: gap != `/Contents` token, no `%%EOF` at the signed end, signature object absent from the signed xref, attached CMS content under a detached subfilter, duplicate keys in a signature dictionary or in any changed object, broken `/Prev` chain, changed signed signature dictionary. Treat reachable-from-AcroForm as a requirement for anything better than Unknown.
3. **Trust (ADR-0012):** use `CustomRootTrust` with a Quire-managed anchor set for AATL/EUTL lists and `X509ChainTrustMode.System` for the Windows store; never write to a store. Default revocation to `NoCheck` plus an explicit "check revocation online" policy, because every online check leaks the cert identity to the CA and the API cannot be told to stay offline for CRLs in any other way.
4. **Writer scope for the first cut:** approval and certification signatures, CAdES B-B and pkcs7 detached, RSA PKCS#1 v1.5 and ECDSA, classic and xref-stream bases, direct/indirect AcroForm shapes, visible appearance generation. Defer: B-T/B-LT timestamps and DSS, document timestamps, PSS, encryption, hybrid-xref and linearization-aware writing, signing files the parser cannot open. Size the placeholder with a dry-run sign (CMS length is deterministic apart from TSA tokens; **untested suggestion**) instead of a fixed 16 KB.
5. **Define the policy for permitted-change overlays** (annotations, form fill, new signature fields) before shipping: the validator can only warn. Consider the visual-diff complement noted in 3.2.3.
6. **Recoverable parsing** needs its own decision: the validator should stay strict, the viewer lenient, and a lenient parse of a signed document must never upgrade a verdict.
