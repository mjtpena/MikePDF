# Performance harness

Master prompt §11 sets the budgets and §15.1 step 7 puts a "performance smoke against budgets" in the pipeline. This directory holds the budgets, the baselines and the notes on how the numbers are made. The tool is `tools/MikePDF.Perf`; its tests are `tests/MikePDF.Perf.Tests`.

**Read this first.** Nothing here proves a budget. R1, R2 and R3 (the reference machines, R-17) have not been confirmed, and GitHub-hosted runners are shared virtual machines. What this harness gives you today is (a) a way to measure every budget that can be measured by software, the same way every time; (b) a gate that catches a 10% regression against a baseline taken on the same kind of runner; and (c) numbers from one development machine, marked as such. When R1, R2 and R3 exist, run `MikePDF.Perf run --profile full --reference-tier R1` on them (see "Reference hardware") and the same files become the evidence for the budgets.

## What is in here

| File | What it is |
|---|---|
| `budgets.json` | Every row of §11: the R1, R2 and R3 target, the statistic compared, which tool measures it, and notes. A test holds it to the §11 table |
| `baselines/*.json`, `*.md` | Result files kept as baselines, one per runner (`ci-x64`, `ci-arm64`, `dev-...`) |
| `README.md` | This file |

## Running it

Build the native engine and the tool, then run (PowerShell 7, Windows 11, no administrator rights):

```powershell
./build.ps1 -Configuration Release -Arch x64 -SkipManaged       # the sandboxed engine
dotnet build tools/MikePDF.Perf -c Release
$perf = (Get-ChildItem tools/MikePDF.Perf/bin/Release -Recurse -Filter MikePDF.Perf.exe).FullName

& $perf run --profile ci   --out perf-results                    # measure; writes perf-results.json and .md
& $perf gate --profile ci  --baseline docs/perf/baselines/ci-x64.json --runner-id ci-x64   # measure and compare, exit 1 on a regression
& $perf compare --baseline a.json --current b.json              # compare two result files
& $perf generate --out docs-out                                  # just write the test PDFs
```

`--profile quick` (1 warm-up, 3 iterations) is for tests, `ci` (3 warm-ups, median of 15; 5 for the heavy scenarios) is what CI runs, `full` (5 warm-ups, median of 30; 9 heavy) is for baselines and reference machines. Exit codes: 0 pass, 1 regression, 2 bad usage, 3 a metric could not be measured.

The harness starts the **real sandboxed engine** (`MikePDF.Engine.exe` in an AppContainer, deployed to `build/out/perf` the way the integration tests deploy it) and talks to it through `MikePDF.Broker`. It never launches the app, registers a package or touches the desktop.

## The test documents

Generated by `Documents/PerfDocuments.cs`, never committed. Plain ASCII PDF, classic cross-reference table, no compression, a fixed pseudo-random generator (SplitMix64) and no dates, so the same spec gives the same bytes on every machine; a test pins the SHA-256 of the 20-page file. Each page is US Letter with a heading, a shaded band, a rule, 46 lines of about 12 words in 10 pt Helvetica, and a page number. Documents over 50 pages use a two-level page tree.

| Id | Pages | Used for |
|---|---|---|
| `text1` | 1 | Cold-open engine share |
| `text20` | 20 | "Typical 20-page PDF": warm open, tile latency and throughput, recovery |
| `text500` | 500 | Search (the word `quokkafish` is on pages 5, 55, 105 … 455, twice on page 5: 11 matches, first on page 5) and engine memory |
| `text2000` | 2,000 | Large-document open |

These are text pages. A scanned, image-heavy, vector-heavy or transparency-heavy file costs PDFium far more per page (spike S2 saw 20 ms for a transparency tile); this suite says nothing about those. The corpus tier (W1-render) is where they belong.

## What is measured and how

All headless metrics are wall-clock, from `Stopwatch` timestamps around broker calls.

| Metric id | §11 row | Method | What it leaves out |
|---|---|---|---|
| `open.warm.first_tile.text20` | Warm open, 20 pages ≤ 250 ms | The app's own open sequence (`DocumentSession.OpenAsync`): start the document engine, open, start the pool engine, open there, document info, first 32 page sizes; then the first sharp 512 px tile (document engine) and the low-res placeholder (pool engine) in parallel. Value: time to the first sharp tile. The earlier of tile and placeholder is in `details.t_first_pixel_ms`, and every stage's time is in `details` | The UI thread: tile upload, drawing, compositing. **A lower bound** |
| `open.cold_engine.first_tile.text1` | Cold open, 1 page ≤ 800 ms | The same sequence on a 1-page file | Process start, XAML, window, drawing. A lower bound. "Cold" is a fresh process with a warm file cache; a cold file cache is not produced |
| `open.large.first_tile.text2000` | 2,000-page first page ≤ 1.0 s | The same sequence on the 2,000-page file | As above. Text pages only |
| `open.engine_warm.first_tile.text20`, `...text2000` | none | Open in an engine that is already running (open, info, sizes, first tile) | Supporting: what reusing the engine across documents would cost |
| `search.first_result.text500`, `search.full.text500` | Search ≤ 300 ms first, ≤ 3 s full | `FindSession` over `DocumentReader` over the pool engine's document, from page 1; the document is reopened for every iteration so no earlier search helps. Each run checks the first match is on page 5 and that exactly 11 matches are found on 500 pages | Highlighting on screen. The first result needs five pages searched, because the generated file puts the first match there |
| `memory.engine_peak_working_set.text500` | Engine memory ≤ 600 MB | A fresh document engine renders every 512 px tile of all 500 pages at 100% (3,000 tiles, 3 in flight); the engine process is read from outside (`WorkingSet64`, `PeakWorkingSet64`, `PrivateMemorySize64`) while it runs and when it stops. Value: peak working set. 1 MB = 1,048,576 bytes | Zoom levels other than 100%, thumbnails (pool engine), several documents |
| `memory.engine_private_bytes.text500` | none | Private bytes at the end of the same run | |
| `recovery.crash_to_first_tile` | Engine crash to restored ≤ 2 s | A fresh supervisor per iteration (so the crash-loop guard never trips): open a 20-page file, render a tile, kill the engine process **from outside**, then ask for the tile again until it arrives. Value: kill to the tile | The in-app banner |
| `recovery.supervisor_restore` | none | The supervisor's own `Restored.Elapsed` | |
| `render.tile_latency.text20` | none | All 120 tiles of the 20-page file one at a time; the iteration's value is the median of its 120 tiles; `details` has the pooled p95 and max | |
| `render.tile_throughput.text20` | none | The same 120 tiles, three in flight, tiles per second | |
| `package.install_size` | Install size ≤ 60 MB | Sum of the file lengths inside a built single-architecture `.msix` (a zip). **Skipped, with the reason, when there is no package** (`build/out/package/MikePDF_<version>_<arch>.msix` or `--package`) | Optional AI models (there are none yet) |
| `package.msix_file_size` | none | Size of the `.msix` file | |

Not measured by this harness, and why:

| §11 row | Status |
|---|---|
| Cold start to interactive window, cold open to first pixel (end to end), scroll frame rate and 50 ms frames, UI process memory | Need the packaged app: the app's ETW markers and `measure-app.ps1` (below). **Not run end to end** |
| Blank area while scrolling | No automated counter exists; spike S2's probe ran on a development machine only |
| Zoom gesture response | Not automated; spike S2 measured it on a development machine |
| Ink pen-to-pixel latency | Needs a Surface with a pen and a high-speed camera (S5, R-17). No ink in the app yet |

## The app's markers (`measure-app.ps1`)

`src/MikePDF.App/Diagnostics/AppTrace.cs` defines an `EventSource` named `MikePDF-App` (GUID `6f1b4a44-3d0e-4c6b-9b64-0d5a1d1f7a21`). It writes nothing anywhere unless an administrator starts a local ETW session for it; there is no telemetry and no payload names a document. The shell calls it in six one-line places:

| Id | Event | Raised |
|---|---|---|
| 1 | `ProcessMain` | first line of `Program.Main` |
| 2 | `WindowInteractive` | after `Root.Loaded`, when the UI thread next goes idle |
| 3 | `OpenRequested(sequence)` | `MainWindow.OpenPathAsync` |
| 4 | `FirstPagePixels(sequence)` | the first draw after an open request that put page content (placeholder or tile) on the surface |
| 5 | `ScrollInput` | `DocumentSession.ScrollBy` |
| 6 | `FramePresented(drawMicroseconds)` | end of each draw of the page surface |

`tools/MikePDF.Perf/measure-app.ps1` (PowerShell 7, elevated) starts a `wpr` session for the provider, launches the app through the `mikepdf.exe` alias on the generated 1-page PDF, waits, optionally flings the page with the mouse wheel (`-Fling`, which drives the real mouse over the window), samples the UI process, stops the trace, reads the events with `Get-WinEvent`, and calls `MikePDF.Perf trace-metrics`. `-EventsCsv` skips the capture and analyses event files (`TimeUtc,EventId,ProcessId`), so a trace made with PerfView or WPA can be analysed too.

| Figure | Definition |
|---|---|
| Cold start to interactive | process creation (the process's own start time, or `ProcessMain` if that is not given) to `WindowInteractive` |
| Cold open to first pixel | process creation to the first `FirstPagePixels` of the process |
| Warm open to first pixel | `OpenRequested` to the next `FirstPagePixels`, for every open after the first |
| Scroll | a burst is scroll input with gaps ≤ 250 ms; only bursts ≥ 2 s count as sustained. Within it: frames per second, median / p95 / max time between draws, and draws more than 50 ms after the previous one. Frames up to 50 ms after the last input belong to the burst; later ones are the page settling |

**Unverified.** The analysis is tested on synthetic traces (`TraceAnalysisTests`), including running the script in `-EventsCsv` mode. The markers inside the running app, the `wpr` capture, `Get-WinEvent` decoding an `.etl` for a provider that is not registered, and the fling have never been run, because the packaged app cannot be launched on the machine this was written on. The first person to run it should expect to fix details. "Frame" means a draw of the page surface into its swap chain: the compositor and scan-out follow up to one refresh later and are invisible to this method (PresentMon sees them but needs administrator rights, spike S2).

## Budgets file

`budgets.json` has one entry per §11 row: `targets` for R1, R2 and R3 (a `null` means §11 sets no number for that tier; §11 says budgets are measured on R1 unless stated, so R2 and R3 repeat R1's where it says nothing, and `targetsInherited` lists those), `measuredBy` (`headless`, `headless-part+app-etw`, `app-etw`, `package` or `manual`), the harness metrics held against it, and `coverage` where a metric is only part of the row (`lower-bound`). In a result file a metric with a budget carries a `budget` object: the target, the tier, whether the median is within it, and `referenceHardware`. **`referenceHardware` is false unless the run was started with `--reference-tier` on a machine that really is that tier**, and the Markdown then says "here (not reference hardware)". A `lower-bound` metric under its target is reported as "engine share only: under target, not a pass".

## The regression gate and its noise policy

§11: "A regression of more than 10% on any budget metric fails the build." R-09 warns that a 10% wall-clock gate on hosted runners "will be flaky". The policy below is built to make that less likely; it is a first version, with numbers chosen by judgement and not yet calibrated against a month of hosted-runner data. **Expect to tune the floors, and to mark individual metrics non-gating, after the first dozen CI runs.**

1. **Median of N.** Each iteration gives one sample after untimed warm-ups (JIT, file cache, first-run allocations). A metric is the median of 15 (5 for search and memory, which take seconds per iteration). The median ignores up to half the samples being slow, which a shared machine produces (another VM, an antivirus scan, a GC); the mean would move with one 100 ms stall. The p95, the minimum, the maximum and the coefficient of variation are in the file so a noisy metric is visible.
2. **Wait for a quiet machine.** The `ci` profile waits up to 20 s (`full`: 40 s) for the whole machine to be under 15% busy before it starts, and the workflow shuts down the compiler servers first (the first CI run found hosted runners 57% to 62% busy in the half second after the build, which made the opens up to 80% noisy). What it read, and how long it waited, are in the result file; a run that never got quiet says its timings are inflated.
3. **Fresh processes where it matters.** Opens start new engines each iteration (as the app does). Memory uses a new engine per iteration. Recovery uses a new supervisor per iteration.
4. **Two conditions to regress.** A metric regresses only if it is worse than the baseline by more than **10% of the baseline** *and* by more than its **absolute floor** (`Metrics/MetricCatalog.cs`: 0.25 ms for a tile, 3 to 8 ms for opens, 25 ms for search and recovery, 8 MB for memory, 1 MB for sizes, 40 tiles/s for throughput). 10% of a 1 ms tile is 0.1 ms, below what a hosted runner's scheduler can resolve; the floors are about a scheduler time-slice or two of jitter, chosen by judgement. A change under its floor is reported as "under the floor" and passes.
5. **Retry the suspects, vote.** After the first run, only the metrics that look regressed are measured again, alone, twice more. Their reported value is the **median of the three run medians**, so a real slowdown must show up in at least two of the three runs, and one bad run is outvoted. The cost is at most two extra runs of the suspect scenarios, not the whole suite. If a run were independently wrong 5% of the time, two of three being wrong would be about 0.7%; runs on a shared machine are not independent (a noisy neighbour lasts minutes), so the real figure is higher. That is the main residual risk.
6. **Per-runner baselines, reviewed.** The baseline is `docs/perf/baselines/ci-<arch>.json` and is only ever changed by a commit someone reviews, never by CI, so slow drift cannot ratchet in. The comparer warns when the baseline's architecture, runner id or CPU differs (hosted runners are drawn from a pool of different VM types).
7. **Cannot measure is a failure; skipped is not.** A metric that errors (the engine will not start, a correctness check fails, the search finds the wrong number of matches) fails the gate. A metric skipped with a stated reason (no package) does not.
8. **No baseline passes, loudly.** The first run on a runner compares nothing, says so in the job summary, and uploads its results as the candidate baseline.
9. **Advisory metrics.** A metric whose `MetricDefinition.Gate` is false is compared and reported but never fails the build. None is advisory today; this is the lever for a metric that proves too noisy on hosted runners.

If the hosted gate proves flaky anyway, R-09's fallback applies: keep these results as trend data, gate on wall-clock only nightly on self-hosted R1/R2/R3, and gate per PR on deterministic proxies (install size and engine memory are already much steadier than times).

## CI

`.github/workflows/perf.yml` runs on every PR and `m*/**` push, nightly, and on demand, for **x64** (`windows-2025-vs2026`) and **ARM64** (`windows-11-vs2026-arm`): build the native engine (`build.ps1 -SkipManaged`), build the tool, run `gate --profile ci` against `docs/perf/baselines/ci-<arch>.json`, write the Markdown to the job summary, and upload `perf-results/` (JSON and Markdown) as an artifact. It is a separate workflow so that it does not collide with edits to `ci.yml`.

**Setting or changing a baseline**: take `perf-results.json` from the artifact of a CI run you judge typical (not one that ran during an incident), commit it as `docs/perf/baselines/ci-x64.json` or `ci-arm64.json` in a reviewed change, and say why. Re-baseline after an intended change in speed (better or worse) and after the hosted image changes the CPU class. These runners are **not reference hardware**: CI numbers say "no worse than last time on this kind of VM", never "meets the budget".

## Reference hardware

When R1, R2 and R3 exist (R-17), on each of them, idle, plugged in, power plan Best performance, nothing else running:

```powershell
$perf run --profile full --reference-tier R1 --runner-id ref-r1 --out perf-results-r1 --package <the .msix for this architecture>
pwsh tools/MikePDF.Perf/measure-app.ps1 -Runs 10 -Fling -ReferenceTier R1 -RunnerId ref-r1
```

Record the exact machine models in an ADR (§11 asks for it; ADR-0001 has none yet) and put them in the `hardware` field of the tier in `budgets.json`. Only then do result files stop saying "not reference hardware".

## What the first measurements already show

`baselines/dev-275hx.md` and `.json` are a `full` run on the development machine (Intel Core Ultra 9 275HX, 24 logical cores, 63 GB, Intel graphics and an RTX 5080 Laptop GPU, Windows 11 26H2, Balanced power plan, plugged in). It was **not an idle machine**: other programs were running, and the file records 32% background CPU use after waiting 40 s for it to drop. It is the baseline for the `dev-275hx` runner id only, and not reference hardware. Two `full` runs a few minutes apart gave a warm open of 72.9 ms and 40.7 ms (the first while other builds were running), which is why the gate takes medians of many iterations, retries, and floors, and why a number from this machine should not be quoted as a result. Two observations that matter for the next waves:

* **The app starts two engine processes for every document it opens** (`DocumentSession`: a document engine, then a pool engine, both new). The harness measures that sequence (`open.warm.first_tile.*`) next to the same open in an already-running engine (`open.engine_warm.first_tile.*`); the gap is the price of two AppContainer process starts. The §11 "warm open (app running)" budget is 250 ms.
* The harness caught a mistake of its own that is worth recording: `RenderTileArgs.TileX/TileY` are **pixel offsets** in the scaled page (as `TileGrid.Rect` produces), not tile indexes. A first version passed indexes and rendered the wrong regions. A test now renders all six tiles of a page and checks which have ink.

## Limits and follow-ups

* `FirstPagePixels` fires on the first draw with page content after an open request. If the surface is redrawn with the previous document's content before the new one's first tile (a window resize during an open, say), a warm open reads too fast. Use warm-open figures from runs where nothing else happens.
* The engine-memory reading was cross-checked once by polling `Get-Process` from a second shell while the scenario ran (21 MB working set, 6 MB private; the harness read 19 MB and 6 MB). The engine's page cache keeps this far below the 600 MB budget on text pages; image-heavy pages will use more.
* Hosted-runner numbers are noisy and not reference hardware; floors and the choice of gating metrics are first guesses.
* The app-level measurements are unverified end to end.
* Text-only documents. No scanned, vector-heavy or transparency-heavy documents until the corpus tier lands.
* Search starts at page 1; a search that starts mid-document, regex and whole-word variants are not measured.
* No deterministic CPU proxy (instruction counts, allocations) yet; R-09 suggests one for per-PR gating.
* Memory is one document at 100%. Zoom levels, several documents and the pool engine are not covered.
* Blank-area and zoom-response need counters inside the app.
